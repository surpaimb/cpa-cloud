# ID-05 employee self-service password-change contract

Status: development preview, default off. This independently authored contract extends the first-stage [employee self-service foundation](employee-self-service-foundation-contract.md); it does not complete GOV-02 or authorize production deployment.

## Scope and provenance

An active, admin-enrolled employee with an existing self-service password may change only their own password through the existing `/self/` page. This adds no registration, email, SSO, recovery, admin reset, API Key, usage, billing, payment, membership, or admin-settings capability. It does not alter the admin authentication domain or model API authentication. The implementation must be newly authored from this contract, not copied or ported from archived CPA, CLIProxyAPI, Sub2API, or nearby reference repositories. It uses the existing Go standard library, `golang.org/x/crypto/bcrypt`, and SQLite driver; no new dependency, DDL, or SDK is planned. Their existing licenses remain theirs. Relevant public behavior is documented by [Go net/http](https://pkg.go.dev/net/http), [bcrypt](https://pkg.go.dev/golang.org/x/crypto/bcrypt), and [SQLite transactions](https://www.sqlite.org/lang_transaction.html).

## Request and response

`POST /self/api/v1/password` is registered only when `--employee-self-service-enabled` is true; otherwise it returns 404. It requires a valid, unexpired self session for an employee whose current status is active. An admin cookie or employee API Key cannot substitute for that session. The request requires exactly one matching `Origin`, `X-Self-Request: 1`, and the current session's `X-CSRF-Token`, compared as in other authenticated self writes. A mismatched or absent write Origin, missing custom header, missing/wrong CSRF token, expired session, or disabled employee cannot mutate the password.

The body is bounded to 4096 bytes and must be a JSON object with exactly two string properties, `current_password` and `new_password`. Unknown, missing, duplicate, non-string, trailing, or malformed data is rejected. Each password must be valid UTF-8 and 12–72 UTF-8 bytes. The service verifies `current_password` against the stored cost-12 bcrypt hash and rejects a new password equal to the current one. Wrong-current and stale-credential failures use a uniform public `invalid_credentials` response; a same-password failure must not reveal the hash or password and may use that same response. Malformed bodies are `400`. The existing bounded peer-plus-employee rate limiter applies to invalid password attempts, including attempts with a valid session. Rate limiting may return `429` and `Retry-After`.

On a confirmed durable commit, the service returns `204` with no response body and clears the `cpa_self_session` cookie with the same path and security attributes. The browser drops the in-memory self session and prompts for a fresh login. No old or new password, hash, session secret, or token appears in a response, log, browser storage, or URL. Password inputs remain native `type=password` fields and are cleared after submission, including failure. The form works at desktop and 390 px widths.

## Atomicity and failure boundary

The service computes a fresh bcrypt cost-12 hash, then in one SQLite transaction conditionally updates only the authenticated employee's password row if its prior hash still matches and the employee is still active, and deletes **all** self sessions for that employee. A zero-row compare-and-swap result is a failed attempt, not a second success. Thus two concurrent changes based on the same old password yield at most one success. Administrative disable/revocation must not interleave so as to reactivate a credential or session. No new session is created by password change.

Any storage, statement, row-count, or commit error fails closed: no `204` and no newly issued credential. On a commit whose outcome is unknown to the handler, it also returns service unavailable and does not claim success. The employee should start a fresh login, trying the proposed new password first and then the previous password; only one may be current. If neither works after rate-limit cooldown, an administrator can disable and re-enable the employee and issue a new enrollment under the existing administrative workflow. There is no silent retry of the password transaction and no new recovery endpoint. Existing database schema validation applies at startup; incompatible old/pre-existing schema fails closed.

## Data inventory and GOV-02 boundary

The only new persisted value is a replacement bcrypt hash in the existing credential row. On success, session selector/verifier digests and CSRF tokens for that employee are deleted. On failure, no credential or session mutation is allowed. Old hashes may persist in SQLite WAL pages or backups until their normal retention/compaction boundary; this feature does not claim immediate forensic erasure. Operators must document internal notice, backup retention, restore treatment, and employee credential recovery before production use. If they cannot, keep the feature flag off. GOV-02 remains open.
