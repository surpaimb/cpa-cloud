# ID-05 employee self Key request activity contract

Status: independently specified development-preview increment, default off. This narrows the existing [employee request activity](employee-self-request-history-contract.md) to one Key visible through the [employee Key inventory](employee-self-key-inventory-contract.md). It complements the [per-Key Token summary](employee-self-key-token-summary-contract.md); it does not settle GOV-02 or authorize production enablement.

## Source, scope, and authorization

An active, admin-enrolled employee with a live independent self session may explicitly read minimal request activity for **one existing API Key that still belongs to that employee**. `GET /self/api/v1/keys/{id}/usage/requests` is available only under the existing `--employee-self-service-enabled` flag, which remains false by default. The existing `requireSelf` boundary verifies optional matching Origin, self-session digest and absolute expiry, and current active employee state. An administrator cookie, employee model Bearer Key, anonymous request, or another employee's self session cannot substitute.

The path Key ID is only a selector; employee identity comes exclusively from the verified self session. A malformed captured ID returns fixed `400 invalid_request`. For otherwise valid requests, missing, foreign, pending, and cancelled-slot Keys return the same fixed `404 not_found`, without an existence hint. An issued self-Key slot is eligible. A revoked or expired Key still owned by the employee remains historically readable; this does not restore model access. No employee, provider, account, model, policy, price, or status selector is accepted. Admin APIs and model authorization do not change.

This specification, source, and tests are independently authored from CPA Cloud requirements and public references, not copied, translated, or ported from archived CPA, CLIProxyAPI, Sub2API, or adjacent reference repositories. ## Request, cursor, and response

The endpoint accepts no body, including unknown-length HTTP/2 DATA. Query keys are only `from`, `to`, `limit`, and `cursor`, each at most once. Unknown, duplicate, empty, malformed, or oversized values return fixed `400 invalid_request` with no data. Explicit `from` and `to` are required together, use whole-second RFC3339 timestamps with an explicit zone, normalize to UTC, and define `[from,to)` with `from < to` and at most 31 days. Without bounds, the first page freezes a recent 24-hour window ending at the next UTC second. Subsequent pages carry that window in the cursor; supplied bounds must exactly match after UTC normalization. Absent `limit` means 20; explicit limit is ASCII decimal 1–50 without a leading zero, sign, or whitespace. A later page may change the limit.

The Key-scoped cursor is a canonical, bounded, versioned base64url payload authenticated with a **new purpose-separated keyed digest**. It binds the verified `employee_id`, path `key_id`, frozen window, and last emitted normalized `(started_at,id)` position. It is not an authorization token. Old all-Key request cursors, Key inventory cursors, summary responses, forged or malformed values, another employee's or Key's cursor, mismatched windows, and stale versions all fail fixed `400 invalid_request`. Every page still repeats session authorization and Key ownership. The cursor does not include plaintext Key material, request content, or browser-persisted state.

Success is exactly `{"items":[...],"next_cursor":string|null}`. Each item is exactly `{"id","key_id","model_id","status","started_at","finished_at"}`; `finished_at` is null only for a pending request. Status is one of `pending|succeeded|failed|cancelled|interrupted`. Times are normalized UTC RFC3339 and preserve nanosecond precision. The response excludes provider, upstream account, attempts, Token values, cost, price, billing, policy, Key secret/digest, prompt, response, and error text. Success and failure carry `Cache-Control: no-store`.

Rows are ordered by actual UTC `started_at` descending and binary `id` descending. The comparison uses the established normalized nine-digit fractional SQL time key rather than raw variable-width RFC3339Nano text. A bounded query scans at most `limit+1` rows, including a validated sentinel for `next_cursor`; it never returns a total count. The cursor records the last emitted row, not the sentinel. Pagination across separate requests is **not a cross-page snapshot**: concurrent inserts or status changes may affect later pages, and the client may restart at page one.

## One-snapshot read and failure boundary

One at-most-five-second, read-only SQLite transaction first confirms both `access_keys.id` and `access_keys.employee_id` match the selector and verified session, excluding a non-issued or mismatched self-Key slot. In that **same transaction**, the page SELECT constrains `accounting_requests` by both `r.employee_id=?` and `r.key_id=?`, the frozen window, and cursor position. There is no ownership check on one connection followed by a page read on another. The handler validates all scanned fields and times, checks iteration and close, checks cancellation, and commits before emitting any success header or item.

Missing/corrupt relevant schema, wrong field type, invalid scanned ID/model/status/time or pending/finished relation, query/scan/iteration/close/commit fault, or cancellation returns fixed `503 storage_unavailable` with no partial items. An owner miss remains `404 not_found`; invalid request syntax or cursor remains `400 invalid_request`. Neither a transaction failure nor a later page may silently fall back to all-Key history. No DDL, ledger write, Key mutation, upstream call, or external-service call is introduced.

## Browser, retention, and release boundary

The `/self/` Key inventory offers an explicit per-Key “查看请求活动” action. Loading the inventory never fans out into per-Key requests. Only the selected Key's bounded first page is fetched; more pages require an explicit action. Switching Key or view, logging in/out, changing session/account, unmounting, or any failed page clears this panel and cursor; an aborted or late response cannot refill stale data. The UI labels the projection as minimal request activity, not complete usage, billing, or compliance evidence. It continues to hide Key policy and persists no session, identity, cursor, or activity in localStorage, sessionStorage, URL, or service-worker cache. Desktop and 390 px rendering are required.

Source data is existing `access_keys`, `employee_self_key_slots`, and `accounting_requests`. There is no new stored personal data or retention timer. Existing ledger/WAL, backups, and restored snapshots retain their base behavior; hiding this projection is not forensic erasure. Operators must settle notice, role access, backup/restore, and retention before production enablement. GOV-02 remains open; otherwise keep self-service off and use administrator-only usage management.
