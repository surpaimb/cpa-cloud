# ID-05 / BILL-03 employee self subscription purchase snapshot

Status: independently specified development-preview contract on exact merged `main` baseline `699d615780365d385ca353ba2bc1ef2598e06cbf`. A draft implementation is under validation; this contract does not establish production readiness. The increment is one default-off, single-subscription historical read. It extends the [self-service foundation](employee-self-service-foundation-contract.md), [own subscription status](employee-self-subscription-status-contract.md), [own wallet balance](employee-self-wallet-balance-contract.md), [single-instance billing](single-instance-billing-contract.md), [frozen subscription period](subscription-period-expiry-contract.md), [manual renewal](subscription-manual-renewal-contract.md), and [typed financial actor provenance](financial-actor-provenance-contract.md). It is not a complete bill or a new financial operation.

## Source facts and evidence boundary

The CPA Cloud write paths record each subscription creation or monthly successor in one SQLite transaction with a subscription row, one `subscription_purchase` ledger operation, exactly one negative `subscription_charge` and one positive `subscription_credit` for the same new subscription, and a `subscription.create` or `subscription.renew` commercial receipt sharing that operation ID. Monthly renewal also records an immutable predecessor-to-successor link. The original employee self-purchase path creates only `one_time` subscriptions; administrator purchase may create `one_time` or `monthly`, and an administrator or the one-shot worker may create a monthly successor. A later, independent [employee self monthly renewal](employee-self-monthly-renewal-contract.md) path may create a monthly successor under its stricter direct-owner and existing-wallet contract. A later change to the commercial execution switch or current plan must not erase this historical read.

These facts support a **local wallet purchase-time cross-check**, not a cryptographic attestation of every displayed field. The account, ledger operation/entries, commercial receipt, and renewal link have existing immutability guards, but `financial_subscriptions` itself has mutable lifecycle fields and no whole-row immutability trigger. In particular, `plan_id`, `plan_revision`, `interval`, and `period_end_at` are controlled-write-path creation records not independently present in the two ledger amounts; `started_at` can be cross-checked against immutable operation and entry times, but is not an external time attestation. The current plan row may have changed. A direct SQL writer able to bypass the service boundary can alter a subscription's plan metadata while leaving a superficially consistent ledger chain. This projection must neither call that metadata tamper-proof nor silently present a broken chain as a verified bill. It validates every cross-check available in the current schema, fails closed on contradictions, and labels the remaining trust boundary. It does not consult the current plan's price or infer payment, tax, invoice, provider cost, model access, or entitlement.

## Activation and authority

Introduce `--employee-self-subscription-purchase-snapshot-enabled`, false by default, and an independent self-session boolean `features.employee_self_subscription_purchase_snapshot`. Enabling it requires **all three** existing opt-ins: `--employee-self-service-enabled`, `--employee-self-subscription-status-enabled`, and `--employee-self-wallet-balance-enabled`. A missing prerequisite fails startup before altering persisted state; setting only a prerequisite never enables this feature. When off, the route is absent (404) and the UI control is absent. The flag is independent of plan catalog, employee purchase, cancellation, one-shot renewal, and `financial_settings.execution_enabled`. Historical reads remain possible while commercial execution is off.

Only a currently active, enrolled employee with a live self-service session can call the endpoint. Use the existing `requireSelf(false)` boundary: optional `Origin` must be same-origin, the self cookie verifier/session expiry and current employee status are checked, and the session's employee ID alone determines ownership. Administrator cookies, employee model Bearer Keys, request-supplied employee/account/owner identifiers, and another employee's self session confer no access. This GET requires no current password, CSRF header, operation ID, or write-side rate limiter. Disabling an employee, logout, session revocation, expiry, or a changed self account removes access under the existing session rules.

## `GET /self/api/v1/billing/subscriptions/{id}/purchase-snapshot`

Accept exactly one bounded, nonempty, opaque subscription ID path segment (maximum 256 bytes under the existing identifier grammar), with no query string **including a bare `?`**, no request body or unknown-length transfer body, and no additional path segment or suffix. Reject decoded slashes, dot-segment/ambiguous encodings (including second-encoded percent escapes and backslashes), oversized ID, duplicate/unknown query fields, and method/path lookalikes without redirecting into an authorized read. For a valid self session, parseable malformed application paths return fixed JSON `400 invalid_request`; a nonexistent subscription, other employee's subscription, or a Key/resource-owned subscription returns uniform `404 not_found`. Authentication failure is `401 authentication_required`; invalid optional Origin is `403 request_rejected`. Middleware may reject an unauthenticated malformed request before route validation. An invalid raw percent escape such as `%ZZ` is rejected by Go's HTTP request-target parser with transport `400` before a request or self session exists; it cannot reach this application route and has no routing or financial side effect. No application JSON error contract applies to that pre-parser rejection.

On success the response has exactly these nine fields and no enclosing list or cursor:

```json
{
  "subscription_id": "subscription_example",
  "plan_id": "plan_example",
  "plan_revision": 3,
  "currency": "USD",
  "interval": "monthly",
  "price_micro": "10000000",
  "credit_micro": "20000000",
  "started_at": "2026-10-02T08:00:00Z",
  "period_end_at": "2026-11-02T08:00:00.000000000Z"
}
```

`plan_revision` is a positive JSON safe integer. `price_micro` and `credit_micro` are positive, canonical base-10 integer **strings** in local wallet micro-units: no sign, decimal point, exponent, or leading zero. `currency` is exactly three uppercase ASCII letters. `interval` is `one_time|monthly`; `period_end_at` is JSON `null` for `one_time` and the frozen, canonical UTC exclusive end for `monthly`. `started_at` is canonical UTC RFC3339Nano. A monthly end obeys the existing one-calendar-month clamping rule and is later than start. The snapshot remains readable for active, cancelled, expired, predecessor, and successor records; no current status, balance, remaining credit, plan name, actor, account/operation/entry ID, digest, payment, tax, invoice, or personal data is returned. There is no pagination or enumeration API in this increment.

`Cache-Control: no-store` applies to success and every application-generated error, including parseable malformed-path responses. Go's pre-request transport `400` for an invalid raw percent escape is outside that application header contract. The browser must not persist this projection in local/session storage or a service-worker cache. A successful response says only what the **local wallet purchase record** captured for this one subscription; it is not today's plan price, current wallet balance or cost, a provider bill, a real-money payment, or proof of usable rights.

## One bounded read-only transaction and chain validation

Use one at-most-five-second cancellable SQLite read-only transaction and prepare the entire response before writing a success header or byte. Validate the exact relevant account/subscription/ledger/commercial/renewal schema, indexes and immutability guards; do not run DDL, create an account, post a ledger entry, invoke a worker, or call an upstream service. Bound each target-related query (for example at most two candidate creation receipts or renewal links and at most three entries, so an extra row is detectable), rather than materializing unrelated subscriptions or the full ledger. The deadline bounds wall-clock work even when an existing lookup lacks a selective index; if it cannot finish, return 503. Do not silently migrate or repair schema during this GET.

1. Load the one subscription and its account in the same snapshot. Check storage types, IDs, positive safe amounts/revision, canonical currency and UTC times, interval/period/state combinations, cancellation-time shape, account currency, and the expected existing plan FK. If the subscription is absent, or the otherwise valid account is owned by another employee or a Key/resource subaccount, return uniform 404. For a direct employee-owned match, require the session employee ID, canonical owner key, `owner_kind='employee'`, NULL Key ID, empty resource fields, and matching account/subscription currency. A malformed account, missing FK, or malformed **owned** row is 503, not a guessed snapshot.
2. Identify **exactly one** creation receipt for this subscription: `subscription.create` or `subscription.renew`, `resource_kind='subscription'`, `resource_id={id}`, receipt revision 1, valid 32-byte digest, and canonical receipt time equal to `started_at`. Another creation receipt, no receipt, an action/resource mismatch, or malformed typed actor is a broken chain. Later cancellation or one-shot receipts are not creation receipts.
3. By that exact global operation ID, require one ledger operation with `action='subscription_purchase'`, the same subscription resource, canonical creation time equal to the subscription and commercial receipt, valid digest shape/version, and the same **stored** actor identity. A create may have the existing admin or employee actor; a renew may have the admin or `subscription_one_shot_worker` system actor. The later [employee self monthly renewal](employee-self-monthly-renewal-contract.md) narrowly adds employee `subscription.renew` only when both commercial and v2 ledger actors are the same current employee ID and the predecessor and successor are directly owned by that employee. Historical `legacy_unknown` is accepted only when both stored sides match the exact pre-actor migration shape and the ledger's legacy digest version; never infer a missing actor or reinterpret it as the current employee. A system create, any other system ID, or cross-side actor mismatch fails closed.
4. Require exactly two entries under that ledger operation and no others: one `subscription_charge=-price_micro`, one `subscription_credit=+credit_micro`. Both must reference the same directly owned account, operation, currency, subscription resource, and canonical `started_at`, with NULL original-entry references and valid entry IDs/types. Checked integer comparisons must not overflow. A missing/extra/wrong-sign, mixed-account/currency/resource/time entry, or a dangling ledger/commercial operation is 503.
5. A `subscription.create` row has no incoming renewal link. A `subscription.renew` row has exactly one immutable incoming link whose successor and operation IDs match the row/receipt. Validate its distinct, existing monthly predecessor, same plan ID and direct employee owner key, predecessor's valid frozen end at or before successor start, terminal expired state, and link time equal to successor/operation start. Do not require the predecessor and successor to use the same currency/account if the current plan's currency legitimately changed at renewal. An outgoing link from this subscription does not invalidate its own historical purchase snapshot. A missing, duplicate, dangling, or contradictory incoming link fails closed.

All scan, row-count, iteration, `Rows.Err`, close, context/deadline, and transaction commit outcomes are checked. A relevant malformed schema or row, broken chain, storage/scan/iteration/close/commit error, or cancellation returns fixed `503 storage_unavailable` with **no partial success fields**. Never turn an inconsistent owned record into a 200 based only on its subscription row. A later request may observe a later SQLite snapshot; this single-item read makes no cross-request consistency promise. Reads and denials leave every financial row and operation count unchanged. No secret, cookie, header, employee Key, raw SQL error, amount projection, or response body is logged.

## Browser and acceptance boundary

In the existing own-subscription list, show this control only when `employee_self_subscription_purchase_snapshot=true`. No snapshot fetch on mount, login, list read, hover, or pagination. The employee explicitly opens one listed subscription's snapshot; at most one target is expanded. Hold results only in component memory. Switching target, list page, self account/session, or logging out clears the former result; an unsuccessful read clears any prior result for that target and shows a sanitized error. Abort in-flight requests and use an identity/request generation check so late responses cannot refill a stale view. Render the nine fields and the local-wallet/not-a-bill caveat clearly on desktop and a 390 px browser viewport without horizontal overflow. A stale list item never overrides server-side ownership or chain checks.

This document states intended behavior; passing checks must be reported separately from untested requirements. Independently authored tests must cover flag combinations/default-off and commercial-off historical reads; session/Origin/administrator/Key/foreign/disabled isolation; strict path/query/body; one-time and monthly, cancelled/expired/predecessor/successor, plan mutation after purchase, admin/employee/worker/exact legacy actors; same-operation two-entry and renewal-link invariants; absent/duplicate/mismatched receipts, ledger/entry/account/owner corruption, direct-SQL tamper boundaries; read transaction concurrency, schema/scan/iteration/close/commit/cancellation faults, no partial response and zero writes; restart/revocation; explicit UI read, target/page/account/logout/failure clearing and late-response suppression on desktop and Chrome 390 px. Test synthetic random non-8787 process flows and report what actually ran separately from what remains planned.

The implementation's merge gate remains exact-HEAD uncached full Go tests, four disjoint complete CGO service-race shards plus the eleven stateful-race packages, vet, both CLI builds, Web typecheck/tests/build, isolated process smoke, and independent same-HEAD fixed-binary acceptance twice. Every new commit reties those proofs to its new HEAD. No DDL, financial write, trial, monthly employee purchase, employee arm, full bill/usage, real payment/provider, deployment, tag, package, or native workflow dispatch belongs to this increment. If the current schema or historical data cannot substantiate one of the nine fields under the limits above, stop and report the concrete blocker instead of widening scope or displaying a doubtful bill.
