# ID-05 / BILL-04 employee self wallet-entry classification contract

Status: independently authored development-preview contract with a local implementation proposed in Draft PR [#53](https://github.com/surpaimb/cpa-cloud/pull/53). The contract itself is not runtime evidence. The flag, read-only route, ledger checks, UI, and focused tests are implemented; exact-head CI, complete fault-injection coverage, GOV-02, and production enablement remain open. This is the next small, default-off increment after the [self-service foundation](employee-self-service-foundation-contract.md), [employee wallet balance](employee-self-wallet-balance-contract.md), [recent wallet activity](employee-self-wallet-activity-contract.md), and [single-instance ledger](single-instance-billing-contract.md).

## Provenance and activation

This contract is derived from CPA Cloud's own requirements and current ledger invariants, not copied, translated, or ported from archived CPA, CLIProxyAPI, Sub2API, or an adjacent reference repository. Public implementation references consulted on 2026-10-03: [Go `net/http`](https://pkg.go.dev/net/http), [Go `database/sql` transactions and row iteration](https://pkg.go.dev/database/sql), [Go `cipher.AEAD`](https://pkg.go.dev/crypto/cipher#AEAD), [SQLite isolation](https://www.sqlite.org/isolation.html), [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html), [SQLite triggers](https://www.sqlite.org/lang_createtrigger.html), and [SQLite `SELECT` ordering](https://www.sqlite.org/lang_select.html). The endpoint, field meanings, and validation policy below are **our specification**, not a provider or SQLite API. Existing Go, SQLite-driver, React, and test dependencies retain their recorded licenses; this increment needs no new dependency, SDK, provider protocol, or payment integration.

The `--employee-self-wallet-entry-classification-enabled` flag is a fourth, independent, false-by-default startup opt-in. It requires all three existing flags: `--employee-self-service-enabled`, `--employee-self-wallet-balance-enabled`, and `--employee-self-wallet-activity-enabled`. A missing prerequisite with this new flag on is a startup configuration error, not a silent fallback. Only an effective combination registers `GET /self/api/v1/billing/entry-classifications` and advertises `features.employee_self_wallet_entry_classification=true` in the authenticated self-session response. The new flag does not turn on commercial execution or any other self feature.

The existing `/self/api/v1/billing/entries` remains a separate endpoint. With activity off, it remains absent (404); with activity on, its six exact top-level fields (`currency`, `has_account`, `window_start`, `window_end`, `items`, `next_cursor`), each item's two exact fields (`occurred_at`, `delta_micro`), error behavior, and existing cursor purpose are unchanged whether the new flag is off or on. In the fourth two-flag combination (new on, activity off), startup is rejected, so neither endpoint is served. No new `entry_kind`, alias, version marker, or new cursor is introduced into the old endpoint; old and new cursors are mutually unacceptable.

Only a currently enrolled and active employee with a live self session can read the new route. The existing self boundary verifies optional same-origin `Origin`, cookie verifier, expiry, and employee status. An admin cookie, employee model Bearer Key, anonymous caller, disabled employee, or another employee's session cannot substitute. The verified session alone supplies employee identity; query or cursor cannot select an employee, account, Key, resource, or another currency. The service releases its initial admission read lock for the ledger read, then takes the admission write lock for the **same** session/active-employee recheck and success output. This serializes success against logout, password change, and administrative disable; a failed final check emits no partial success.

## Exact read API and response

`GET /self/api/v1/billing/entry-classifications?currency=USD[&limit=20][&cursor=...]` accepts exactly one three-uppercase-ASCII-letter `currency`. An optional canonical decimal `limit` is 1–50 and defaults to 20 on the first page. Continuation must explicitly repeat the authenticated first-page limit. The optional cursor is a bounded canonical base64url token and only accompanies that explicit limit. The raw query is at most 2048 bytes and the cursor at most 1024 bytes. Duplicate/unknown keys, empty or noncanonical values, malformed encoding, excess length, or any request body (including unknown-length HTTP/2 transfer) return fixed `400 invalid_request`. There is no currency discovery, bulk request, account selector, or alternate route; only the exact GET can succeed.

The response has exactly the old page's six top-level fields, but belongs to this **new** route and has one additional raw field per item:

```json
{
  "currency": "USD",
  "has_account": true,
  "window_start": "2026-09-02T12:00:00Z",
  "window_end": "2026-10-03T12:00:00Z",
  "items": [{"occurred_at":"2026-10-03T11:59:59Z","delta_micro":"-42","entry_kind":"adjustment_debit"}],
  "next_cursor": null
}
```

`entry_kind` is the **stored ledger kind**, not a reconstructed business source or label. It is one of the closed set `adjustment_credit`, `adjustment_debit`, `topup`, `redemption`, `subscription_charge`, `subscription_credit`, `refund`, `usage_charge`. In particular, `adjustment_debit` can also carry an existing commercial top-up refund; it must not be described as necessarily a manual adjustment. `usage_charge` is an allowed ledger category, not evidence of a production usage-charge posting. Neither a category nor a signed amount proves an external refund, payment, bill, model usage charge, actor, subscription ID, entitlement, or why a transaction occurred. The API exposes none of those assertions or underlying IDs, resource fields, operation digest, account details, current balance, or other employee's facts.

`delta_micro` is the selected immutable entry's nonzero signed integer micro-amount rendered as a canonical base-10 string; `occurred_at` is its canonical stored UTC `RFC3339Nano` timestamp. Missing direct employee wallet account returns `has_account:false`, `items:[]`, `next_cursor:null`; a present account with no matching entry returns `has_account:true` and the same empty array. Neither state is a balance or proof that a present account is zero. Key-owned and resource-owned subaccounts are never merged into this view.

## Window, order, and isolated cursor

The first read freezes the same 31 × 24-hour UTC window as the old activity route: `window_end` is the next whole UTC second after receipt, exclusive; `window_start` is 31 days earlier, inclusive. Each subsequent page uses the same bounds but a fresh read-only database snapshot. Its order is the existing immutable `(created_at TEXT, id TEXT)` pair descending in SQLite binary text order, with a strict `<` continuation predicate and `limit+1` selected rows to determine `next_cursor`. The raw `RFC3339Nano` text may sort differently from nanosecond chronology within the same second because fractional precision varies. This is a stable **stored-key** order, not a promise of exact subsecond ranking or a cross-page consistent snapshot. Concurrent posts may appear or be missed across pages according to their stored position. Whole-second indexed range comparison must preserve the activity route's inclusive/exclusive boundary behavior.

The new cursor uses the existing installation secret and authenticated encryption with a fresh nonce, but an independent version-1 purpose, `cpacloud/self-wallet-entry-classifications-cursor/v1`; it never shares the old activity cursor purpose. Its authenticated plaintext contains only employee ID, current self-session selector, currency, window bounds, limit, and the last stored time/ID position. Before any ledger read, verify AEAD authentication, canonical encoding and structure, version and purpose, current identity/session, currency, limit, exact 31-day window, position within that window, and that continuation is less than 15 minutes after the original `window_end`. Tampering, truncation, wrong installation/purpose/version/session/employee/currency/limit, or expiry returns fixed `400 invalid_request`. It is not persisted in the database or browser storage. Cursor encryption or serialization failure is `503 storage_unavailable`, before any success header.

## One bounded read and minimal ledger cross-check

Use one at-most-five-second read-only SQLite transaction, with no DDL or write. Validate the **exact existing** `financial_accounts`, `financial_operations`, and `financial_entries` table/index definitions, declared foreign keys, and their immutable update/delete triggers, not just object names. This does not require an all-history integrity scan. Select at most two matching accounts for `owner_kind='employee'`, the authenticated employee, and the requested currency; validate the single account's owner key, `key_id IS NULL`, empty resource fields, storage types, and canonical time. Duplicate or malformed matching accounts fail closed. Query only that account's entries in the frozen window and page position, at most `limit+1`, and validate the lookahead row as well as returned rows.

For each selected entry, validate stored identifier/text/integer types, canonical UTC time, nonzero amount, closed kind, and sign. Join its `operation_id` to exactly one existing immutable `financial_operations` row; validate the operation's action, actor-kind/ID-column shape and selected admin/employee actor FK target existence, `digest_version` integer in `{1,2}`, and `payload_digest` as a 32-byte BLOB. `legacy_unknown` is acceptable only in its historical version-1/null-actor shape; system actor shapes remain limited to the existing callback/one-shot-worker action combinations. The operation and entry must have **identical stored** `created_at`, `resource_kind`, and `resource_id`, with well-formed IDs. Neither actor nor digest leaves the API. Do not recompute the payload digest: historical payloads and operation context are not universally reconstructible from this page.

The action/kind/sign matrix to verify for every selected entry is:

| Stored operation `action` | Allowed selected `entry_kind` | Sign | `original_entry_id` |
| --- | --- | --- | --- |
| `adjustment` | `adjustment_credit`, `adjustment_debit` | positive, negative respectively | absent |
| `topup`, `payment_callback` | `topup` | positive | absent |
| `redemption` | `redemption` | positive | absent |
| `subscription_purchase` | `subscription_charge`, `subscription_credit` | negative, positive respectively | absent |
| `refund` | `refund`, `adjustment_debit` | positive, negative respectively | required |
| `usage_charge` | `usage_charge` | negative | absent |

For a selected `refund` entry, its original must be a negative `adjustment_debit`, `subscription_charge`, or `usage_charge` entry in the **same account**. For a selected `refund`-action `adjustment_debit`, its original must be a positive `topup` entry in that same account. The original ID must be a valid non-null reference; all other selected entries must have no original ID. Check each distinct referenced original and its relevant reversal siblings in this same snapshot: sibling account, allowed reversal kind/sign/reference, checked magnitude addition, and cumulative reversal no greater than the original magnitude. A single bounded scan may group distinct originals; at most 100,000 relevant reversal rows may be examined per request, with excess, overflow, malformed sibling, or deadline failure returning 503. The validation is **ledger-layer only**: do not traverse commercial receipts, payment/top-up/refund/redemption/renewal business tables, infer external settlement, or validate unrelated ledger history.

Check query iteration, row close, context, transaction commit, final self-session validity, and cursor encoding before emitting any success header or byte. Missing/changed relevant schema or trigger, broken selected foreign key, malformed selected operation/entry/original/sibling, account mismatch, SQL/scan/iteration/close/commit error, timeout, or cancellation returns fixed `503 storage_unavailable` and **no partial page**. Auth failures retain the self boundary; syntax and cursor failures return 400 as above. Success and failure use `Cache-Control: no-store` and fixed redacted messages. Do not log cookies, cursors, employee identifiers, amounts, digests, raw SQL errors, credentials, prompts, or model responses.

## Browser and release boundary

The self page exposes a separate classification control only when its own capability is true. The employee types one currency and explicitly clicks to open/read it; mount, login, changing currency, or opening the old activity view must not fan out into this route or enumerate currencies. Keep items and cursor in component memory only. A currency or account/session switch, logout, unmount, and **every** failed read clear the old result and continuation; abort plus request-generation/identity guards discard late responses. A next-page click explicitly uses the same currency/limit and may not mix windows. Desktop and 390 px views distinguish missing account from present-but-empty, display raw `entry_kind` without a misleading business-source translation, and show signed amount. Do not persist employee identity, currency, result, cursor, or session material in localStorage, sessionStorage, page URL, or a service-worker cache. The API request necessarily carries currency/cursor in its URL and must be `no-store`.

There is no new table, migration, persisted fact, financial write, worker, provider call, payment/refund operation, subscription entitlement, invoice, release, tag, package, deployment, or multi-instance guarantee in this increment. Existing ledger/WAL, backup, restore, and retention remain unchanged; hiding the view does not erase data. Production enablement still requires GOV-02 notice, role/retention, and recovery decisions. This contract alone does not establish any tested runtime behavior.

## Acceptance boundary and current evidence

Independently written tests must cover the four new/activity flag combinations and all prerequisite failures; old `/billing/entries` exact JSON shape and cursor-purpose compatibility under every valid combination; route separation and cross-purpose cursor rejection; strict query/body parsing; anonymous/admin/Bearer/self, Origin, disable/logout/expiry/restart, cross-employee/session/currency, and Key/resource isolation; missing versus empty account; all eight raw kinds including commercial `adjustment_debit` and allowed-but-not-produced `usage_charge`; both signs, mixed-precision/same-key ordering, page boundary, concurrent post, tamper and age; schema/FK/trigger, operation actor/digest version/length, action/kind/sign/time/resource, original/sibling/cumulative reversal corruption; 100,000-row cap, iteration/close/commit/cancel faults, final-session race, and zero partial output. Browser tests must prove explicit click/no mount fan-out, old-view independence, account/currency switch, failure/late-response clearing, and desktop/390 px rendering. Prove no new stored facts or upstream traffic and no secret/amount logging.

The current local implementation has passed targeted Go tests (including selected/original/sibling orphan actors, malformed-path no-redirect cases, and controlled logout/password-change races across the final success boundary), vet, Web typecheck and focused UI tests, an isolated dynamic non-8787 process smoke, and real Chrome desktop/390px checks. The earlier implementation HEAD also passed the full Web test suite and build; this follow-up changes no Web source. The broader planned cases above are not all automated: the 100,000-row cap, iterator/close faults, some cursor age/tamper variants, and administrative-disable race still need targeted coverage. A concurrent full Go run on Windows timed out during local SQLite/fixture I/O; a separate serial Windows run also timed out after 15 minutes in the pre-existing service suite and had one temp-database file-lock cleanup failure. Neither run is a full-Go PASS. Exact-latest-HEAD GitHub full Go, actual race, both CLI builds, Web, and the newly wired classification process smoke need separate results; the prior GitHub run lacks the new smoke and cannot provide them. Keep PR #53 Draft until its latest HEAD and independent fixed-binary acceptance are reviewed. No package, tag, release, or deployment is implied.
