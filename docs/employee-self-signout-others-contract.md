# ID-05 employee self sign-out-other-devices contract

Status: independently specified development-preview increment, default off. This extends the [self-service foundation](employee-self-service-foundation-contract.md) and [password change](employee-self-password-change-contract.md), without completing GOV-02 or authorizing production enablement.

## Scope, provenance, and authority

An already enrolled, active employee may invalidate their *other* browser self sessions after proving possession of their current password in their current valid self session. The session, not any request field, determines the employee. An administrator cookie, employee model Bearer Key, anonymous request, or another employee's session is not a substitute. The existing `--employee-self-service-enabled` flag gates the page and endpoint; when off, the endpoint is 404. No administrator session, employee API Key, model request, upstream credential, ledger, or billing state changes. No new configuration, DDL, dependency, external service, device inventory, session count, or individual-device selector is introduced.

This specification and its implementation/tests are authored from CPA Cloud's functional requirements and public documentation, not copied or ported from archived CPA, CLIProxyAPI, Sub2API, or adjacent reference repositories. Public behavior references checked 2026-10-01: [Go `net/http` routing/body limits](https://pkg.go.dev/net/http), [Go `database/sql` transactions](https://pkg.go.dev/database/sql), [bcrypt](https://pkg.go.dev/golang.org/x/crypto/bcrypt), and [SQLite isolation](https://www.sqlite.org/isolation.html). Existing Go, SQLite driver, React, and test dependencies retain their recorded third-party licenses. No new dependency or SDK is needed; new source carries explicit provenance.

## POST /self/api/v1/sessions/revoke-others

The route requires a valid, unexpired self cookie for an active enrolled employee, the existing exact matching `Origin`, exactly `X-Self-Request: 1`, and that session's `X-CSRF-Token`. Query parameters are rejected. The body is at most 4096 bytes and exactly one JSON object with the sole string field `current_password`. Missing, duplicate, unknown, non-string, trailing, malformed, or oversized input returns fixed `400 invalid_request`. In particular, the request cannot name an `employee_id`, target selector, target device, or session list. The supplied password must be valid UTF-8 and 12–72 UTF-8 bytes and match the existing cost-12 bcrypt hash. Wrong/stale passwords return fixed `401 invalid_credentials`; the existing bounded peer-plus-employee limiter includes malformed, invalid, and wrong-password attempts and may return `429 login_limited` with `Retry-After`. Authentication fails before account data is disclosed. Errors are fixed and redacted, and responses use `Cache-Control: no-store`.

After a confirmed durable commit, the server returns `204` with no body and no session count, selectors, timing, or credential details. Exactly the other `employee_self_sessions` rows for the current employee are removed; the current selector, verifier, expiry, and CSRF token remain unchanged. Zero other sessions is also a `204`. On a subsequent request, each removed session gets an authentication failure, while the current session remains usable. The endpoint neither invalidates administrator sessions nor changes employee API Keys. It does not imply erasure of historical metadata.

## Transaction, concurrency, and failure boundary

The initial cookie digest, expiry, active employee, Origin, custom header, and CSRF checks may occur under the existing admission read lock. That read lock must be released before acquiring the exclusive lock; lock upgrade is forbidden. Body parsing and bcrypt comparison occur outside the exclusive lock. The final SQLite write transaction under `admission.Lock` rechecks the same current selector and employee, current session expiry, active status, and the exact password-hash version that passed bcrypt. It then deletes rows for that employee whose selector differs from the current selector. No target chosen by the browser participates in SQL. The durable commit is the success linearization point; logout, password change, administrator disable, and concurrent sign-out-others must serialize with it. A competing request from a just-revoked session fails its final recheck rather than claiming success. Different employees' operations must not delete each other's sessions.

Any begin/query/delete/commit error or unknown commit outcome returns fixed `503 storage_unavailable` and never a success-shaped response. No automatic retry is performed. A client may retry from the still-valid current session; if the earlier uncertain commit did occur, zero remaining other sessions is a valid `204` only after the retry confirms its own transaction. The implementation does not log the password, cookie, CSRF, hashes, session selectors, request body, or database error text. Cancellation before confirmed commit cannot be called success.

## Browser and retention boundary

The self page offers an explicit two-step action: first reveal confirmation, then enter the current password and submit. Password text lives only in transient component memory, is cleared on success and every failure, logout, account/session switch, cancellation, and unmount, and never enters browser storage, URL, telemetry, or rendered error text. A confirmed `204` leaves the current device signed in; a `503` never displays a claim that other devices were signed out. Render and interact correctly at desktop and 390 px. No session count or device inventory appears.

Existing session rows may have appeared in SQLite WAL pages, backups, or restored snapshots. Removing active rows blocks subsequent self authentication, but is not a forensic erasure or a substitute for retention policy. Internal notice, backup/restore handling, retention, and access review remain GOV-02 work; otherwise the feature stays off. It must not be described as complete self-service or compliance.
