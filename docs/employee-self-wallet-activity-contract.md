# ID-05 / BILL-03 employee self wallet-activity contract

Status: independently specified development-preview increment, default off. This extends the [employee self-service foundation](employee-self-service-foundation-contract.md), the [employee wallet-balance projection](employee-self-wallet-balance-contract.md), and the existing [single-instance financial ledger](single-instance-billing-contract.md). It is a minimal view of recent changes to the employee-owned wallet, **not** a complete bill or accounting export. GOV-02 remains open.

## Provenance, activation, and authority

This specification is independently authored from CPA Cloud requirements and public documentation, not copied, translated, or ported from archived CPA, CLIProxyAPI, Sub2API, or adjacent reference repositories. Public references consulted on 2026-10-02: [Go `net/http`](https://pkg.go.dev/net/http), [Go `database/sql` transactions](https://pkg.go.dev/database/sql#DB.BeginTx), [Go authenticated encryption (`cipher.AEAD`)](https://pkg.go.dev/crypto/cipher#AEAD), [SQLite isolation](https://www.sqlite.org/isolation.html), [SQLite date/time text and fractional-second behavior](https://www.sqlite.org/lang_datefunc.html), and [SQLite `SELECT` ordering/limits](https://www.sqlite.org/lang_select.html). Existing Go, SQLite-driver, React, and test dependencies keep their recorded licenses. This increment adds no dependency, SDK, external provider, or payment protocol.

`--employee-self-wallet-activity-enabled` is a separate, false-by-default startup opt-in. It requires **both** `--employee-self-service-enabled` and `--employee-self-wallet-balance-enabled`; either missing prerequisite makes the configuration invalid rather than silently activating anything. The activity route is absent (404) while its own flag is off. It does not enable `financial_settings.execution_enabled`, any commercial write, or the existing balance feature. The effective self-session response exposes `features.employee_self_wallet_activity` only when all three gates are enabled. The old balance endpoint and admin/model endpoints keep their behavior.

Only an enrolled, currently active employee with a live self-service session may read. The existing self boundary checks the optional same-origin `Origin`, keyed cookie verifier, absolute expiry, and employee status under its admission lock. An administrator cookie, employee model Bearer Key, anonymous caller, disabled employee, expired session, or another employee's session cannot substitute. The verified self session supplies employee identity; query strings and cursors cannot choose an employee, account, Key, or resource. A cursor is additionally bound to the current self-session identity so another device/session of even the same employee cannot reuse it. Logout and revocation invalidate both access and continuation.

## `GET /self/api/v1/billing/entries?currency=USD[&limit=20][&cursor=...]`

The request has exactly one `currency` parameter with three uppercase ASCII letters (`[A-Z]{3}`). `limit` is optional on the first page, defaults to 20, and when present is a canonical decimal integer from 1 through 50 (no leading zero or sign). A continuation must explicitly repeat the first page's `limit`; it must equal the authenticated cursor's bound limit. `cursor` is optional only on the first page and is a bounded base64url token. No other query key, duplicate key, malformed encoding, oversized query/token, empty value, or request body (including unknown-length HTTP/2 transfer) is accepted: fixed `400 invalid_request`. There is no bulk-currency or account-enumeration route.

The first request freezes a UTC window of 31 times 24 hours: `window_end` is the next whole UTC second after receipt and is exclusive; `window_start = window_end - 31 days` is inclusive. Thus the current partial second can appear, and a concurrent new entry in that second may be visible on a later page. Both bounds remain unchanged on continuation. A continuation older than 15 minutes from its original `window_end` is invalid and requires a fresh first page. Every page is a new read-only SQLite snapshot, **not** a cross-page database snapshot; an entry added later behind the position may appear, while one added before it may not. No completeness claim is made under concurrent posting.

Each page returns exactly this shape (with 0–50 items):

```json
{
  "currency": "USD",
  "has_account": true,
  "window_start": "2026-09-01T12:00:00Z",
  "window_end": "2026-10-02T12:00:00Z",
  "items": [{"occurred_at":"2026-10-02T11:59:59.123Z","delta_micro":"-42"}],
  "next_cursor": null
}
```

`delta_micro` is the immutable entry's signed amount, represented as a canonical base-10 integer string in micro-units; positive and negative entries are both shown. `occurred_at` is the canonical UTC timestamp already stored for that entry. A missing employee-owner account returns `has_account:false`, `items:[]`, and `next_cursor:null`; an existing account with no entries in this window returns `has_account:true` with the same empty list. A true zero **balance** is not represented by a zero entry (entries are nonzero) and must not be inferred from a page. The response includes no operation/entry/account ID, actor, plan, price, payment, note, resource metadata, current balance, or other employee's facts.

Within one page, position is the immutable pair `(created_at TEXT, entry id TEXT)` in descending SQLite binary text order, using the existing account/time/id index. The encrypted cursor stores the last returned pair; the next page uses a strict `<` pair predicate, so entries sharing the exact stored time do not repeat or skip by id. All accepted entry timestamps are canonical UTC `RFC3339Nano`. Because that format omits trailing fractional zeros and may omit the fraction entirely, raw text order is **not guaranteed to equal strict nanosecond chronological order within one second** (for example `.1Z` and `Z`). The product describes this as stable recorded-key order within the frozen window, not a nanosecond-accurate time ranking. Whole-second window bounds use their 19-character UTC prefix in the indexed text range so fractional and whole-second spellings at either bound are included/excluded consistently. No new index or rewritten timestamp is introduced.

The cursor is versioned, purpose-separated authenticated encryption under the instance's existing persistent secret, with a fresh random nonce. It contains only the employee and current self-session identity, currency, window bounds, limit, and last stored position; its encrypted form does not disclose IDs in the browser or logs. Canonical structure, current identity, currency, limit, window age/order/duration, position within the window, and authentication are checked before any ledger read. Tampering, truncation, wrong installation, wrong purpose, another employee/session, mismatched currency/limit, or old version returns fixed `400 invalid_request`; cursor data never selects a different owner. No cursor is written to the database or browser storage.

## Bounded read and failure behavior

One at-most-five-second read-only transaction validates the existing financial table/index/immutable-trigger schema, then selects at most two matching `financial_accounts` rows for `owner_kind='employee'`, the authenticated employee, and the explicit currency. It validates that the single account's immutable `owner_key` and `key_id IS NULL`/empty resource fields have the employee-only shape. It never folds in Key-owned or resource-owned accounts. The entries query reads only that account in the frozen whole-second window, strictly after the cursor position if present, in the stable order above, and fetches at most `limit+1` rows to determine whether a continuation exists. It checks relevant selected row storage types, canonical timestamp, allowed kind/sign, nonzero signed integer amount, and identifier shape; it checks query iteration, close, context, and transaction commit before emitting any success header or byte. There is no DDL, account creation, ledger write, external request, or full ledger sum.

Missing/malformed relevant schema, duplicate or malformed matching account, malformed selected entry, SQL query/scan/iteration/close/commit failure, timeout, or cancellation returns fixed `503 storage_unavailable` with zero partial items. Cursor encryption/serialization failure also returns 503 before output. Authentication and syntax errors follow the boundaries above. Responses use `Cache-Control: no-store` and sanitized error messages. The service does not log cookies, cursor contents, employee identity, amounts, credentials, prompts, model responses, or raw SQL errors.

## Browser, storage, and release boundary

The `/self/` page shows a separate recent-wallet-activity control only when the independent capability is true. It requires the employee to type a currency and explicitly open/read; mounting, login, or changing currency never enumerates wallets or automatically fetches entries. The page keeps result and cursor only in component memory. Currency changes, self account/session changes, logout, unmount, and any failed page read clear prior items and continuation; abort and request-generation guards prevent a late response from repopulating stale state. The next-page control explicitly fetches with the same currency/limit and must not mix pages from different windows. Desktop and 390 px layouts distinguish missing account from present-but-empty and show signed changes without suggesting they are a bill. Identity, amounts, cursor, and session material are not written to localStorage, sessionStorage, the page URL, or a service-worker cache; the request necessarily carries currency and cursor in its API URL and remains no-store.

This increment adds no table, migration, stored personal data, financial mutation, payment/refund interface, employee purchase, invoice, tax document, membership flow, or multi-instance coordination. Existing ledger, WAL, backup, and restore retention remain unchanged; hiding the view does not erase data. Production enablement still requires GOV-02 notice, role/retention, and recovery decisions. The opt-in remains off otherwise; it is not part of preview.3 packages.
