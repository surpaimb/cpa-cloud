This extends the [self-service foundation](employee-self-service-foundation-contract.md), [password change](employee-self-password-change-contract.md), and [Key inventory](employee-self-key-inventory-contract.md). ## Scope, provenance, and authority

An active, already enrolled employee with a valid independent self session may revoke only an existing API Key owned by that employee. The verified session is the sole source of employee identity; the path Key ID is only a target, never authority. Anonymous callers, administrator sessions, employee model Bearer Keys, and another employee's self session cannot substitute. The existing `--employee-self-service-enabled` flag gates both page and route; when off, the route is 404. Administrator Key creation, listing, policy, and revocation; model authorization; and the existing Key metadata projection retain their meanings. There is no self Key creation, plaintext redisplay, rotation, policy change, billing, membership, payment, new schema, or external service in this increment.

The specification, implementation, and tests are independently authored from CPA Cloud's functional contracts and public documentation, not copied or ported from archived CPA, CLIProxyAPI, Sub2API, or adjacent reference repositories. Public behavior references checked 2026-10-01: [Go `net/http` routing and request bodies](https://pkg.go.dev/net/http), [Go `database/sql` transactions](https://pkg.go.dev/database/sql), [bcrypt](https://pkg.go.dev/golang.org/x/crypto/bcrypt), and [SQLite transaction isolation](https://www.sqlite.org/isolation.html). Existing Go, SQLite driver, React, and test dependencies keep their recorded third-party licenses. No new dependency or SDK is introduced; new source carries an explicit provenance comment.

## POST /self/api/v1/keys/{id}/revoke

The endpoint requires a valid, unexpired self session whose employee is currently active, one exact matching `Origin`, exactly `X-Self-Request: 1`, and the session's `X-CSRF-Token`. No query parameters are accepted. The Key ID must be a bounded valid existing Key identifier. A malformed, absent, or another employee's Key ID returns the same fixed `404 not_found`, without revealing whether another employee's Key exists. No employee selector is accepted. A non-self caller fails authentication before Key lookup. The request body is at most 4096 bytes and exactly one JSON object containing one string field, `current_password`; missing, duplicate, unknown, non-string, trailing, malformed, or oversized input returns fixed `400 invalid_request`.

The supplied password must be valid UTF-8 and 12–72 UTF-8 bytes. The service compares it with the existing cost-12 bcrypt hash; a wrong or stale password returns fixed `401 invalid_credentials` without Key-existence information. The existing bounded peer-plus-employee limiter applies to wrong, malformed, and invalid password attempts; it can return `429 login_limited` with `Retry-After`. No plaintext password, hash, Key selector/digest/plaintext, account detail, or arbitrary SQL error appears in any response or log. All responses use `Cache-Control: no-store`.

For an owned Key not yet revoked, a confirmed durable transaction sets the existing `revoked_at` once and returns `204` with no body. A valid owner/password repeat for an already revoked Key also returns `204` and leaves its original `revoked_at` unchanged, including when an administrator revoked it first. An expired but not revoked owned Key can be revoked and becomes `revoked` in the existing inventory projection. The browser refreshes the owner's inventory after a confirmed `204`; it never treats a `503` or uncertain commit as success. Admin and self revocation use the same underlying Key state, but the self endpoint must never call an administrator's ID-only update as its authorization check.

## Transaction and concurrency boundary

The endpoint first validates the cookie, session digest, expiry, active employee, Origin, custom header, and CSRF under the existing `admission.RLock`, then releases that read lock **before** acquiring `admission.Lock`. Body parsing and bcrypt work occur without an exclusive admission lock. Because logout, password change, disable, and administrator revocation can happen during this gap, the final write transaction under `admission.Lock` rechecks the same session selector's employee and current expiry, active employee status, the password hash version that passed bcrypt, and the target Key's ownership. A stale selector, changed password, or disabled employee cannot produce a successful self revocation. The transaction is one atomic state decision: update only an owned unrevoked Key, or observe its existing non-null revocation timestamp for idempotent success. An absent/foreign Key is 404 even when another employee owns the ID. The lock is never upgraded while its `RLock` is held.

`admission.Lock` serializes the successful commit with administrator revoke, logout, password change, disable, and the model coordinator's final authorization/dispatch transaction (`admission.RLock`). The linearization point for a new revocation is its durable commit. A final dispatch committed before that point may have already entered `MayHaveSent` and can continue; this feature does not promise to interrupt an already dispatched stream or undo an upstream request. A final dispatch reached after the revocation commit rechecks Key state and must reject before a new upstream attempt or network request. Queue waiters are notified through the existing account-pool change signal after a confirmed commit, so stale queued authorization cannot silently become a new dispatch. Two self devices may race: one sets the timestamp, the other may return idempotent `204`, but the timestamp is not replaced. An administrator racing self revocation obeys the same first-commit-wins timestamp rule.

Any database begin/query/statement/row-count/commit error, or a commit whose outcome is unknown to the handler, returns fixed `503 storage_unavailable` with no `204` and no success-shaped body. No automatic retry writes a second timestamp. A client may retry with the same password and Key ID: if the first commit actually succeeded, the idempotent path reports `204` without changing the timestamp. A best-effort account-pool wake on an uncertain commit is advisory only, not a success claim. The service does not add a second process, service call, or Key cache authorization shortcut.

## Browser and retention boundary

Only items in the signed-in employee's Key inventory have a revoke control, and only when not already revoked. A first click reveals an inline confirmation; a second explicit submit requires the current password in a native `type=password` field. The password exists only in this mounted component's transient memory, is cleared on every completion/failure, logout, account/session switch, and unmount, and is never placed in localStorage, sessionStorage, IndexedDB, URL, telemetry, or error text. The UI uses only same-origin relative API paths and renders at desktop and 390 px. A failed read or mutation does not display a Key as revoked merely because a button was clicked. The existing administrator page and model API behavior are unchanged.

The only durable change is `access_keys.revoked_at` in an existing Key row. Existing Key metadata, keyed digest, historical ledger references, SQLite WAL pages, backups, and restored snapshots remain under their base retention behavior; revocation prevents later authorization but is not forensic deletion. The interface must not claim full self-service, compliance, or complete erasure. Internal notice, backup/restore handling, retention, and access review must be settled before production enablement. GOV-02 remains open; otherwise leave self-service off and use administrator-only management.
