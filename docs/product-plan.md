# 第一版产品与架构计划

状态：规划，2026-09-22。没有已经实现的服务端或客户端。

## 产品范围

一家企业部署一套。管理员创建员工并交付 Key，员工使用自己的 AI 工具。
独立开源项目，吸收 CLIProxyAPI 的协议接入能力和 Sub2API 的管理体验作为产品目标；
实现依据公开协议和本项目规格，不复用这两个项目的实现。

## 架构提案

单个 Go 服务承载管理 API、静态网页和模型 API，但管理员会话与员工 Key 严格分权。
React 网页作为构建产物嵌入服务；SQLite 用于第一版单机持久化；优先 Docker Compose 部署。
上述技术选型为提案，待详细设计与验证。

模型请求：客户端 → HTTPS 入口 → 员工鉴权 → 模型权限 → 原生上游适配器 → 上游。
以上鉴权和执行在一个服务进程中，不引入 CPA Cloud 到另一个模型代理的 HTTP 跳转。
若部署使用 TLS 反向代理，应如实标注这一网络跳点，不混同于第二层模型业务代理。

## 功能优先级

| 阶段 | 范围 | 验收 |
| --- | --- | --- |
| P0 接入闭环 | 管理员初始化与登录、上游 API Key、员工、一人多 Key、模型权限、标准协议 | 创建 Key 后可调用模型，撤销确认后新请求被拒绝 |
| P1 可维护性 | 用量持久化、账号状态、脱敏诊断、备份恢复、升级回滚 | 重启不丢统计，备份可恢复，流式及并发测试通过 |
| P2 账号与体验 | 有公开授权依据的 OAuth 适配、账号池调度、会话保持、CC Switch 配置验证 | 按提供商列出实际支持范围及端到端证据 |
| P3 可选员工端 | 独立实现配置管理、安全密钥保管、备份恢复、模型同步 | 不强制安装，和标准客户端执行相同服务端权限 |

P0 优先走有正式公开文档的上游 API Key 接入。OAuth 或订阅账号转换不能因为参考产品支持就承诺支持；
需逐提供商核实可用文档、授权流程及允许的使用方式。没有公开协议依据的接入暂不纳入。

## 核心业务约定

- 员工字段：姓名、可选部门、备注和启停状态；无员工自助注册或充值。
- 每个员工可有多个 Key，分别命名用途；默认不绑定硬件。Key 可设有效期并单独撤销。
- 停用员工使所有关联 Key 失效。明确正在流式输出的请求在撤销时如何处理，并单独测试。
- 模型权限支持全部可用模型或显式列表；目录不得暴露未授权模型。
- Key 明文只在创建时交付，不提供再次读取接口；丢失时生成新 Key 并撤销旧 Key。
- 统计以请求、员工、Key、模型、上游为维度；区分输入、输出及上游提供的缓存 Token。
- 成本估算不等于实际账单；未知用量不能伪造为精确值；重试不能重复计算员工请求数。
- 默认不增加员工预算硬限制。限额、限流、多租户、支付和多节点高可用不属于第一版。

## API 兼容目标

逐项依据官方文档设计并验证 /v1/models、/v1/responses、/v1/chat/completions 和 /v1/messages。
不是一次宣称全部兼容：每种协议需单独覆盖流式、工具调用、错误、取消和模型支持范围。
优先同协议上游转发；跨协议转换须有独立规格和测试，不静默丢弃不能表达的能力。

## 首轮详细设计

已形成[核心设计提案](core-design.md)和[验收矩阵](acceptance-matrix.md)，尚未实现。
下列主题在提案中细化；密码算法参数、完整协议字段与运维工具仍需在对应实现前确认。

1. 管理员登录会话、CSRF、初始凭据交付和尝试限流。
2. Key 摘要、上游凭据加密、安装主密钥保护和备份恢复。
3. 数据模型、事务、撤销生效确认及鉴权缓存一致性。
4. 首个协议与提供商、模型目录、错误映射和流式生命周期。
5. 用量事件、幂等键、故障恢复、保留期及审计脱敏。
6. 开源许可证权利人署名和发布前依赖清单。
