# ID-05 employee self Key issuance contract

Status: independently specified development-preview increment, default off. This is a deliberately narrow, administrator-reserved **single Key slot**: the employee activates a new credential for that exact slot once. It is not permission to create arbitrary Key IDs or copies of existing Keys. Implementation, verification and GOV-02 review remain separate gates; this contract does not authorize production enablement.

## Evidence, provenance and reason for the narrower boundary

CPA Cloud's existing `governance_policies` and `governance_general_budget_policies` address a Key by its concrete `access_keys.id`; request admission resolves them with `auth.KeyID`. A newly inserted Key ID does not share another Key's rolling RPM, concurrency reservations or budget window. Copying another Key's policy values while leaving the old Key usable would therefore allocate additional independent capacity. No employee action may do that implicitly.

This contract derives from CPA Cloud's own [self-service foundation](employee-self-service-foundation-contract.md), [Key inventory](employee-self-key-inventory-contract.md), [Key revocation](employee-self-key-revocation-contract.md), [Key policy](key-account-group-policy-contract.md) and [governance](governance-management-contract.md) specifications and the repository's current store/runtime interfaces. Public behavior references checked 2026-10-01: [Go `net/http`](https://pkg.go.dev/net/http), [Go `database/sql`](https://pkg.go.dev/database/sql), [SQLite isolation](https://www.sqlite.org/isolation.html), and [React input](https://react.dev/reference/react-dom/components/input). New source and tests must be independently authored, not copied or ported from archived CPA, CLIProxyAPI, Sub2API, or adjacent reference repositories. Existing Go, SQLite driver, React and test dependencies retain their recorded licenses; no new dependency or provider SDK is required.

## Authority and finite grant

- `--employee-self-service-enabled` remains false by default. When off, all new self routes and slot administration routes return 404. Admin sessions, model Bearer Keys and self cookies remain mutually non-interchangeable.
- An administrator reserves a **new, never-used** `access_keys.id` for one active, enrolled employee. Reservation creates the Key row and its Key policy but emits no plaintext Key. The row has a purpose-separated, random, discarded placeholder selector/digest to satisfy existing NOT NULL/UNIQUE constraints; the model API, directory, background and final dispatch gates must additionally reject every non-issued slot independent of whether that placeholder could be guessed. The reserved row has no previous usage, reservation, response resource, or historical Key secret.
- One employee may have at most **one self-issuance slot for the lifetime of that employee ID**, including cancelled and issued slots. This limit is enforced by a unique database constraint, not an in-memory count. A lost issued secret is not reissued or redisplayed. The administrator can revoke that Key and use the existing administrator-only Key creation path. A revoked, expired or previously issued Key ID can never become a slot or be reactivated.
- Before arming, the administrator configures the slot's exact Key policy and Key-scoped limits using the existing admin interfaces. Arming requires a nonempty explicit selected client-protocol allowlist and a nonempty explicit selected public-model allowlist; `all` is not accepted for these two dimensions. Source/CIDR and account-group policy are administrator-chosen and still intersect current employee policy and routes. The slot's `expires_at` is administrator-chosen, defaults to no expiry, and cannot be set or extended by the employee.
- Arming also requires enabled global governance and an enabled policy scoped to this **same Key ID** with both a positive RPM and a positive concurrency limit. It requires enabled general hard budget and an enabled, `deny_unknown` Key-scoped catch-all (`protocol=''`, `model=''`) with a positive token and/or cost limit. Unsupported or unbounded model requests can fail closed under that strict budget; arming is not a claim that all model/provider combinations have a proven budget bound. Missing, disabled, malformed, or conflicting controls make arming fail closed. An administrator may choose tighter selectors in addition to the catch-all.
- The arm operation captures the employee revision, Key policy revision, Key expiry, global governance/budget settings revisions, and a canonical digest of **all** Key-scoped governance and budget policy rows (including IDs, enabled flags, selectors, limits and revisions). This is a logical freeze: admin edits may proceed, but any changed snapshot invalidates activation until the administrator reviews and arms the same unused slot again. The employee cannot alter the snapshot, grant, Key name, policy, expiry or limits. After issuance, later administrator changes retain their existing semantics and are not silently blocked by this feature.
- Issuance **does not insert another Key row or policy scope**. It changes only the armed slot's selector/digest and state within one transaction, preserving the exact Key ID whose limits were configured. It does not copy counters, clone a policy to a second ID, reset an existing Key window, or revive a revoked Key. Creation of the dormant slot is an explicit administrator allocation of additional capacity, shown as such in the admin UI; the employee cannot allocate capacity.

## Routes and responses

All writes require the existing exact Origin, role-specific custom request header and CSRF validation. Bodies are at most 4096 bytes for self and at most the existing admin limit for admin, with exactly one JSON object, no duplicate/unknown fields or trailing data; all queries are rejected. IDs and text have explicit existing bounds. Errors are fixed and redacted; every self response and any response containing a slot or one-time Key is `Cache-Control: no-store`.

| Route | Input | Confirmed result |
| --- | --- | --- |
| `POST /admin/api/v1/employees/{id}/self-key-slot` | `{name,operation_id,expires_at?,policy}`; complete Key policy required | `201` with slot ID, name, pending state, expiry and policy; **never** a Key plaintext |
| `POST /admin/api/v1/keys/{id}/self-key-slot/arm` | `{expected_employee_revision,expected_key_policy_revision}` | `200` with armed state and bounded non-secret policy/limit summary |
| `POST /admin/api/v1/keys/{id}/self-key-slot/cancel` | empty object | `204`; permanently cancels an unused slot and revokes its dormant Key row |
| `GET /self/api/v1/key-slots` | no body/query | `200` with at most one own armed slot's ID, name and expiry; no policy internals or secrets |
| `POST /self/api/v1/keys/issue` | `{slot_id,current_password}` | `201` with ID, name, expiry and newly generated `cpac_...` Key, once, only after confirmed commit |

The admin existing Key list exposes an explicit `pending|armed|issued|cancelled` issuance state for slot rows. The ordinary self Key inventory excludes pending/armed/cancelled rows and shows an issued Key under its existing metadata/status contract. Ordinary Key rows have no issuance state in their existing API behavior. The browser labels a slot as an administrator-authorized additional Key, not an extension of an existing Key's quotas. It never presents pending as a usable or active credential.

The self issue route obtains employee identity solely from the verified self session; `slot_id` is a target, not authority. An absent, foreign, cancelled, unarmed, expired, revoked or already-issued slot does not yield plaintext and must not reveal another employee's existence. A current password of 12–72 UTF-8 bytes is checked against the existing cost-12 bcrypt hash; the existing bounded peer-plus-employee limiter covers malformed and wrong-password attempts. Authentication failure, Origin/custom-header/CSRF rejection, and storage failure retain fixed distinct classes without database details.

## Durable state and concurrency

Add an `employee_self_key_slots` table with `employee_id` as a permanent unique key, unique FK `key_id` to `access_keys`, a constrained state (`pending|armed|issued|cancelled`), arm snapshot/digest fields, timestamps and constraints. The migration is additive, transactionally idempotent and validates the exact table/index schema on startup; old databases default to **zero grants**. It never drops or rewrites old Key rows. A malformed pre-existing schema fails startup. SQLite WAL/backup snapshots may retain slot metadata and Key digests; issuance is not forensic erasure.

Reservation and arming run under the existing exclusive admission lock and a write transaction. Reservation verifies a fresh Key ID, active enrolled owner, one-lifetime uniqueness and complete policy insert. It uses a separate `operation_id` namespace and fingerprint for safe admin retries; retry never returns plaintext. Arming re-reads the slot, owner, Key policy, Key expiry, governance settings/policies and general budget settings/policies in one transaction, validates the above requirements, and stores the canonical snapshot. A slot is not automatically armed by the global self-service flag or by merely having a valid self session.

The self handler initially validates the self cookie digest, absolute expiry, active employee, Origin, `X-Self-Request: 1` and `X-CSRF-Token` under the admission read lock, then **releases** that lock before bcrypt and the exclusive lock. It generates a fresh selector and 32-byte secret using `crypto/rand`, but emits neither before commit. Its final transaction under the exclusive admission lock rechecks the same session selector, employee and expiry, active/enrolled status, the exact password-hash version that passed bcrypt, ownership and armed state of the slot, unrevoked/non-expired Key, and an unchanged arm snapshot including the configured Key policy/limits. It then updates the **same** Key row's selector and keyed digest and marks the slot issued atomically. One concurrent issuance wins; a stale second attempt receives a fixed conflict without plaintext. Admin disable, policy/limit edits, slot cancellation/revocation, self logout/password change and competing issue serialize or invalidate the final recheck. A final model dispatch can start only after the issued state commits and must still perform its usual current policy/limit checks.

Any begin/read/write/row-count/commit failure, unknown commit outcome or cancellation before confirmed commit returns fixed `503 storage_unavailable` and no Key, cookie or success-shaped body. The server does not retry an uncertain write. Retrying after a commit that actually succeeded returns already-issued conflict **without redisplay**; the administrator's recovery path is to revoke the issued Key and create/hand over a new Key through the existing admin-only flow. If the commit did not occur, an authorized employee may retry while the slot remains armed. No handler logs plaintext, placeholder secret, password, cookie, CSRF, keyed digest, prompt, model response, or raw SQL error.

## Browser, compatibility and verification gate

The `/self/` page shows only the current employee's own armed slot and a two-step confirmation requiring current password. On confirmed `201` it shows the new Key plaintext once with a copy control and explicit “copy now; it cannot be shown again” message. The Key and password exist only in mounted component memory; they are cleared on leave/unmount, logout, account/session switch, cancellation and every failure. No local/session storage, URL, telemetry, service-worker cache or later API response contains plaintext. Desktop and 390 px widths must remain usable. A failed/unknown commit never displays a claimed success or stale secret.

Existing administrator Key creation/revocation, policy editing, model APIs, ledger, scopes and unrelated self endpoints retain their behavior. The additive gate must be audited at initial Bearer authentication, model directory, queued/background work and final dispatch so a pending row is never interpreted as active. Admin Key list, self inventory, usage/observations and backups distinguish a pending slot from traffic-bearing issued Keys. No upstream, payment, membership, new provider, second service or mandatory client is introduced. GOV-02 remains open: internal notice, retention, backup/restore and role review must be established before production use; otherwise leave the flag off and use admin-only Key management.
