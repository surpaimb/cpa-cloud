# ID-05 / BILL-03 employee self wallet-balance contract

Status: independently specified development-preview increment, default off. This extends the [employee self-service foundation](employee-self-service-foundation-contract.md) and reads the existing [single-instance financial ledger](single-instance-billing-contract.md). It does not settle GOV-02 or authorize production use.

## Source, scope, and activation

This specification and its implementation are independently authored from CPA Cloud requirements and the public references below, not copied, translated, or ported from archived CPA, CLIProxyAPI, Sub2API, or adjacent reference repositories. Public implementation references consulted on 2026-10-01: [Go `net/http`](https://pkg.go.dev/net/http), [Go `database/sql` transactions](https://pkg.go.dev/database/sql#DB.BeginTx), [SQLite snapshot isolation](https://www.sqlite.org/isolation.html), and [SQLite aggregate overflow behavior](https://www.sqlite.org/lang_aggfunc.html). Existing Go, SQLite driver, React, and test dependencies retain their recorded licenses. This increment introduces no dependency or SDK and no external payment/provider protocol.

`--employee-self-wallet-balance-enabled` is an independent, false-by-default startup opt-in. It requires the existing `--employee-self-service-enabled` flag; a wallet-on/self-off configuration is rejected at startup. The self page and all `/self/` APIs remain 404 while the base self flag is off. When only the base flag is on, the wallet endpoint remains 404 and the balance control is absent. Neither the existing financial schema, `financial_settings.execution_enabled`, nor the base self flag automatically enables this projection. The authenticated self session response exposes only a boolean `features.employee_self_wallet_balance` so the page can gate its control. Existing admin billing and employee model APIs are unchanged.

Only an active, admin-enrolled employee with a live independent self session may request the balance. The existing `requireSelf` boundary verifies the optional same-origin `Origin`, keyed session verifier, absolute expiry, and current active employee status. An admin cookie, employee model Bearer Key, anonymous request, or another employee's self session cannot substitute. The verified session is the **only** source of `employee_id`; there is no employee, account, owner, Key, resource, or currency-list selector in the request beyond the single explicit currency. Disable, logout, expiry, and restart follow the existing self-session rules; an unexpired persisted session remains valid after an ordinary restart.

## GET /self/api/v1/billing/balance?currency=USD

The endpoint accepts exactly one query key, `currency`, occurring exactly once. It must be three uppercase ASCII letters (`[A-Z]{3}`); absent, duplicate, empty, lower/mixed-case, Unicode lookalike, encoded extra keys, malformed or oversized query strings return fixed `400 invalid_request`. No request body is accepted, including unknown-length HTTP/2 bodies. An optional `Origin` must match. There is no default currency, bulk enumeration, pagination, or continuation token.

The `200` response has exactly these fields:

```json
{"currency":"USD","has_account":true,"amount_micro":"0"}
```

`amount_micro` is a canonical signed base-10 integer string in micro-units when `has_account` is true: no plus sign, leading zeros, decimal point, exponent, or negative zero. A balance may be negative if existing financial operations allow it. A genuine account with offsetting entries or no entries returns `has_account:true` and `"0"`. If no employee-owner account exists for that employee and currency, the response is `{"currency":"USD","has_account":false,"amount_micro":null}`. It does **not** create an account or imply a zero balance. There is no `account_id`, entry, operation, plan, price, credit, payment, Key/resource balance, another employee's data, or authorization material in either response.

## Read and failure boundary

The balance read uses one at-most-five-second, read-only SQLite transaction. Within that snapshot it finds at most one existing `financial_accounts` row whose `owner_kind='employee'`, `employee_id` is the verified session employee, and `currency` is the explicit parameter. It verifies the immutable account's owner key and employee-only shape (`key_id IS NULL`, empty resource fields) and reads only `financial_entries` linked to that account. Key-owned and resource-owned accounts are never added, even if they share the same employee ID and currency. It validates relevant schema and account/entry storage types, entry sign/kind invariants, and checked signed-64-bit addition in deterministic entry order. At most 100,000 entries may be examined per request; exceeding that limit fails closed. SQL work, result count, and response size are bounded. The transaction is committed and its outcome checked before any success header or byte is emitted. A concurrent writer may become visible on a later request but cannot mix snapshots within one response.

Missing or malformed relevant schema, malformed matching account or entry, duplicate employee-owner account, wrong numeric type, sum overflow, entry bound exceeded, SQL query/scan/iteration/close/commit failure, deadline, or cancellation produces fixed `503 storage_unavailable` with no partial balance. Authentication failures use the existing self boundary; invalid request syntax uses `400 invalid_request`. Success and failure have `Cache-Control: no-store`, fixed sanitized messages, and no raw SQL or secret material. The endpoint performs no DDL, account creation, ledger write, external request, or logging of employee identity, balance, cookies, or credentials.

## Browser, persistence, and release boundary

The `/self/` page shows the balance control only when both startup opt-ins are effective. The employee must type one currency and explicitly click to read it; mounting, login, and currency changes never fetch, infer, or enumerate accounts/currencies. The browser stores the result only in component memory. Changing currency, switching the self account/session, logout, unmount, or any failed read clears the prior result; abort/identity guards prevent a late response from restoring it. Desktop and 390 px views must display the account-present and no-account states distinctly without storing identity, currency, amount, or session material in localStorage, sessionStorage, the **page** URL, or a service-worker cache. The single-currency API request necessarily carries `currency` in its query string and uses `Cache-Control: no-store`.

This feature adds no database table, persisted personal data, migration, financial write, payment flow, entitlement, employee self-purchase, renewal, email, invoice, or multi-instance coordination. Existing ledger/WAL, backups, and restored snapshots retain their base retention behavior; hiding the projection is not erasure. Operators must resolve employee notice, role access, retention, and recovery before production enablement. GOV-02 remains open; otherwise keep the wallet opt-in off and use administrator-only billing views.
