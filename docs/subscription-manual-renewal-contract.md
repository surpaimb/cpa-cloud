# Manual renewal of an expired monthly subscription (BILL-03)

This independently authored development-preview increment extends the [single-instance billing contract](single-instance-billing-contract.md) and [single-period expiry contract](subscription-period-expiry-contract.md). It permits an administrator to buy one new monthly period for an already due monthly subscription using that owner's existing single-instance wallet. It is not automatic renewal, a model entitlement, an employee self-purchase, or an external payment. Commercial execution remains off by default.

## Request and authority

- `POST /admin/api/v1/billing/subscriptions/{id}/renew` accepts only bounded JSON `{ "operation_id": "..." }`. `{id}` is the predecessor; the server derives its owner and plan. No client-selected price, period, owner, successor, or effective date is accepted. The existing administrator session, write Origin/CSRF checks, and commercial execution switch apply. The response contains the existing receipt shape and the newly created subscription, including the predecessor link. The operation action is `subscription.renew`.
- The operation identity is the existing global operation ID plus administrator actor, action, and canonical request payload digest, including the path predecessor ID. An exact retry returns the first successor without reposting money or recomputing dates. Reusing an ID with another path, actor, action, or payload conflicts. A retry of an already committed renewal remains readable if the commercial switch was subsequently turned off; a new renewal is refused while off. A failed transaction creates neither success receipt nor successor/link/money.
- A missing predecessor is 404. A cancelled, `one_time`, not-yet-due, or already renewed predecessor is a conflict. A monthly predecessor is due at `period_end_at <= transaction UTC now`, including the exact endpoint, even if the expiry worker has not persisted `expired`. The endpoint checks and conditionally persists the due predecessor's terminal `expired` state and one revision increment in the same transaction. A previously cancelled row is never changed. Administrative reads still project effective expiry while the worker lags.

## Atomic financial transition

- Within one SQLite transaction, the predecessor must still belong to an existing valid employee/Key/resource owner and be monthly with a valid frozen end. The renewal resolves the *currently enabled* plan with the same immutable plan ID, then freezes its current revision, `price_micro`, `credit_micro`, currency, and monthly interval into a **new** subscription. A changed/disabled/deleted/non-monthly plan is a conflict. The predecessor's original plan snapshot and ledger entries never change.
- The server obtains the owner wallet account for the current plan currency through the existing ledger identity validation, derives its balance through the immutable entries, and requires enough balance for the entire charge. Exactly one existing-ledger debit `subscription_charge` and one grant `subscription_credit` are posted for the new subscription. Zero amounts retain existing ledger rules. The operation receipt, predecessor-expired transition (when needed), new subscription, permanent predecessor→successor link, and both entries commit together or roll back together. SQL/ledger/commit uncertainty is reported as unavailable, never as a fabricated success; the same operation ID can be queried by retry after recovery.
- The successor starts at the transaction's captured UTC time, not at the predecessor's old end; a delay is not retroactively covered. Its exclusive `period_end_at` is exactly one calendar month later under the frozen month-end clamping rule. Thus a January 31 renewal may end on February 28/29; a renewal at March 31 ends April 30. A successor is `active`, revision 1, and may itself later expire and be renewed. No expired credit is reclaimed and no refund is implied.
- A durable append-only relationship has unique predecessor ID, unique successor ID, and unique renewal operation ID. These constraints prevent two distinct operation IDs from creating separate successors for one predecessor, including concurrent requests and post-restart retries. A losing request rolls back its candidate subscription and all ledger effects and returns conflict or an unavailable serialization error; it never returns a second success. Link/list/detail reads fail closed on corrupt ownership, period, or link data.

## Migration and presentation

- Schema migration recognizes exactly the immediately preceding billing schema. It updates the allowed commercial-operation action set and adds the renewal relationship inside a single transaction, preserving every old operation/subscription/entry unchanged. Unexpected schema, malformed existing data, failed foreign-key validation, or injected persistence failure rolls back to the previous usable schema. Reopening a migrated database is idempotent. Newly introduced source and tests are CPA Cloud-authored; no new third-party dependency is needed.
- Admin subscription list/detail return nullable `predecessor_id` and `successor_id` alongside existing snapshots, effective status, and period bounds. The browser presents an explicit manual-renew action for due monthly rows, the resulting new period and both directions of the chain; server checks remain authoritative. This display makes no claim that subscription status authorizes model requests. The expiry worker continues to expire periods only and never charges or renews.

## Acceptance boundary

Tests exercise exact retry and changed-payload conflict; two concurrent operation IDs against one predecessor; due instant and worker-lag transition; cancelled and `one_time` isolation; disabled switch and plan; current-plan snapshot and currency; insufficient balance and ledger failure; month-end/leap dates; transaction failure/rollback, old-schema migration/restart, and link corruption. Service tests cover admin auth/Origin/CSRF, list/detail, and error mapping. Browser checks use desktop and 390px layouts against an isolated dynamic-port process with synthetic data. Report tested behavior separately from future provider/payment or entitlement work. Exact-head CI must include Go tests/race/vet/build, Web typecheck/test/build and applicable process smokes; do not trigger package/native installer workflows for this feature.
