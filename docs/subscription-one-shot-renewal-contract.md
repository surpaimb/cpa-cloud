# One-shot scheduled wallet renewal of a monthly subscription (BILL-03)

This independently authored development-preview increment extends the [single-instance billing contract](single-instance-billing-contract.md), [single-period expiry contract](subscription-period-expiry-contract.md), and [manual-renewal contract](subscription-manual-renewal-contract.md). An administrator may explicitly arm **one** future wallet-funded renewal for an active monthly predecessor, or disarm it before execution commits. Nothing is armed by default. This is not a standing auto-renew setting: an executed successor has no inherited reservation. It does not grant model entitlement, accept employee self-service, initiate external payment, notify users, refund, or coordinate multiple service instances.

## Authority and API

- `GET /admin/api/v1/billing/subscriptions/{id}/one-shot-renewal` is an administrator-only, no-query read. It returns a bounded projection: predecessor ID, frozen due instant, reservation state (`none`, `armed`, `disarmed`, `succeeded`, `failed`, `superseded`, or `cancelled`), reservation revision, terminal reason code, and successor ID when known. No wallet secret, operation digest, or administrator credential is returned. Missing predecessor is 404; inconsistent stored state fails closed with 503.
- `POST /admin/api/v1/billing/subscriptions/{id}/one-shot-renewal` accepts only `{ "operation_id": "...", "expected_revision": 1 }`. The revision is the predecessor's stored subscription revision. It requires the existing administrator session, write Origin/CSRF policy, and commercial execution enabled. At transaction time the predecessor must be stored `active`, monthly, before its frozen `period_end_at`, not cancelled, and without a successor or prior reservation. The server creates a durable `armed` reservation and a separate cryptographically random internal execution operation ID; the client cannot choose the future plan, amount, owner, clock, successor, or execution ID.
- `POST /admin/api/v1/billing/subscriptions/{id}/one-shot-renewal/disarm` accepts only `{ "operation_id": "...", "expected_revision": n }`, referring to the current reservation revision. The same administrator guards apply. An `armed` reservation becomes terminal `disarmed` if execution has not committed. Disarm does not require the commercial switch to be on. A completed or terminal reservation is read-only. For this deliberately narrow one-shot increment, disarm is final: the same predecessor cannot be armed again; create a new eligible successor through an explicit manual renewal if a later period is desired.
- Arm/disarm use the existing global commercial-operation identity (operation ID, administrator actor, action, canonical path-and-revision payload digest). Exact retries return the stored reservation/current result without a second mutation. Reusing an ID with changed actor, path, action, or payload conflicts. Status reads may observe progress after the original arm response. Employee Keys cannot call these endpoints. The browser uses a dedicated capability flag, explicit confirmation, and server-authoritative refresh; it must not portray an armed reservation as a guarantee that a charge will succeed or as an ongoing auto-renew toggle.

## Durable state and transaction ordering

- A new reservation table has one row per predecessor and a unique stable internal execution operation ID. It stores the arm actor and operation ID, frozen due instant, state/revision, terminal code/time, and optional successor. Identifiers and the frozen due instant cannot change. The prior subscription, wallet entries, commercial receipts, and predecessor→successor link retain their existing immutable protections. All timestamps are canonical UTC; the due boundary is inclusive (`period_end_at <= transaction now`). Schema constraints plus transactional validation reject malformed states and broken foreign keys.
- State transitions are `none -> armed -> succeeded | failed | disarmed | superseded | cancelled`. No terminal state transitions back to `armed`, and no reservation is copied to a successor. `superseded` means an administrator's manual renewal committed first; `cancelled` means the predecessor cancellation committed first. Either transition includes its known final link/reason. A due reservation can remain `armed` during temporary storage unavailability, with a visible pending/due state; it is not reported as successful or failed merely because time passed.
- A bounded in-process worker scans at most 16 due `armed` predecessor IDs in `(due_at, predecessor_id)` order per pass, promptly after startup and periodically. It uses a cancellation-aware bounded pass and stops/joins on service close. The existing expiry worker remains separate and continues only `active -> expired`, including while commercial execution is off. Neither worker contacts a provider or payment connector.
- For each due reservation, the worker begins a SQLite transaction and first reconciles the stable internal operation ID and unique predecessor link. A matching committed renewal is recorded/read as `succeeded`; a different committed link is `superseded`. It then re-reads reservation, predecessor, commercial switch, plan, owner, and balance in the same transaction. Disarm, cancellation, manual renewal, settings changes, and worker claims serialize through SQLite writes; a losing writer rolls back and re-reads rather than returning a second success.
- Only if still `armed` and eligible does the worker execute the *same* financial transition as manual renewal: conditionally persist due predecessor expiry when needed; resolve the currently enabled monthly plan by immutable plan ID; freeze its **current** revision, price, credit, currency, and interval into a new active subscription; derive the current owner's wallet balance from immutable entries; require the full charge; append exactly one `subscription_charge` and one `subscription_credit`; insert the commercial receipt and unique predecessor→successor link; and mark the reservation `succeeded` with the successor. All of those effects commit in one transaction under the stable internal execution operation ID. The worker's money operation has a null administrator actor; the separate arm fact retains who authorized the reservation. A successor starts at the transaction UTC clock, not at the old end, and ends one clamped calendar month later.
- If the switch is off, the current plan is disabled/deleted/non-monthly, funds are insufficient, or the predecessor was cancelled or manually renewed first, the worker persists a fixed, non-secret terminal reason and **no** scheduled money operation. Later funding, plan edits, or re-enabling commercial execution do not retry a terminal reservation. Structural corruption and SQL/ledger/persistence errors instead return unavailable without inventing a terminal business result; the next pass can retry the same stable identity after recovery. A commit error is never reported as success. On restart or uncertain commit, recovery first checks the internal operation fact and unique link; it only attempts a fresh transaction if neither exists, and it never changes the internal operation ID.
- Manual renewal and cancellation update any still-armed reservation to `superseded` or `cancelled` within their own successful transaction. A failed manual attempt changes nothing. Disarm/cancel committed before the scheduled transaction prevent its money effects; if the scheduled transaction committed first, later disarm/cancel cannot undo it. Balance/plan/status errors must not leave a charge, grant, receipt, link, or fabricated successor.

## Strict migration, rollback, and observability

- Migration accepts the exact immediately preceding commercial schema and the exact older commercial-action schema already recognized by the prior migrator; lookalikes are rejected. In one transaction it expands the commercial action allowlist for arm/disarm, creates the reservation table/indexes/guards, validates existing subscription/link/operation/ledger facts and foreign keys, then commits. Old databases have **zero** reservations, even for active monthly subscriptions. Reopening is idempotent; malformed data, injected DDL/copy failure, or foreign-key failure leaves the prior database usable. Rolling back the program requires restoring the matching whole-data-directory backup, including key material; an old executable must not open the migrated database.
- Arm/disarm and terminal result writes contain no Key, upstream token, prompt, response, card/payment payload, or wallet secret. Existing fixed-message error mapping and log secrecy apply. Status is a single consistent read; corrupt owner/link/reservation combinations return 503 rather than an apparently armable row. No customer-facing entitlement, automatic retry notification, tax invoice, or cross-instance lock is implied.
