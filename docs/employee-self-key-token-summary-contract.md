# ID-05 employee self Key Token summary contract

Status: independently specified development-preview increment, default off. This extends the [self-service foundation](employee-self-service-foundation-contract.md), [Key inventory](employee-self-key-inventory-contract.md), [request activity](employee-self-request-history-contract.md), and [all-Key Token summary](employee-self-token-summary-contract.md). It does not settle GOV-02 or authorize production enablement.

## Source, scope, and authorization

An active, admin-enrolled employee with a live independent self session may explicitly request a read-only summary of known Token values and unknown attempts for **one existing API Key that belongs to that employee**. `GET /self/api/v1/keys/{id}/usage/summary` is available only when the existing `--employee-self-service-enabled` flag is on; it remains off by default, and all `/self/` paths remain 404 when off. The route uses the existing `requireSelf` boundary: optional Origin must match when present, session digest and absolute expiry must be valid, and the employee must still be active. An administrator session, employee model Bearer Key, anonymous request, or another employee's self session cannot substitute.

The path Key ID is only a selector. The employee ID comes exclusively from the verified self session; the request cannot select an employee, model, provider, upstream, account, status, price, or currency. Malformed captured Key IDs return fixed `400 invalid_request`. Missing, foreign, pending, or cancelled slot Keys return the same fixed `404 not_found` without an existence hint. A Key that still belongs to this employee remains historically readable after revocation or expiry; these states do not restore its model access. An issued self-Key slot is treated as an existing Key. Administrator APIs and authorization are unchanged.

This source and its tests are independently authored from this contract and existing CPA Cloud specifications, not copied, translated, or ported from archived CPA, CLIProxyAPI, Sub2API, or adjacent reference repositories. ## Request and response

The endpoint accepts no body, including unknown-length HTTP/2 DATA. Its only query keys are `from` and `to`, each at most once and required together. Unknown, duplicate, empty, malformed, fractional, oversized, or unmatched parameters return fixed `400 invalid_request` without data. Explicit bounds are whole-second RFC3339 timestamps with a zone, normalized to UTC, and define `[from,to)` with `from < to` and duration no more than 31 days. With neither bound, the server freezes the recent 24-hour window ending at the next UTC second. The parent `accounting_requests.started_at`, not attempt timestamps, selects the window by actual UTC nanosecond order using the established normalized nine-digit SQL time key.

The successful `200` response has exactly the existing all-Key summary shape, with all counts and sums canonical nonnegative decimal strings:

```json
{"from":"2026-09-30T00:00:00Z","to":"2026-10-01T00:00:00Z","requests":{"total":"2","pending":"0","succeeded":"1","failed":"1","cancelled":"0","interrupted":"0"},"attempts":{"total":"3","pending":"0","input_tokens":{"known_total":"15","unknown_attempts":"1"},"output_tokens":{"known_total":"2","unknown_attempts":"1"},"cache_read_tokens":{"known_total":"0","unknown_attempts":"2"},"cache_write_tokens":{"known_total":"0","unknown_attempts":"2"}}}
```

`requests` counts each matching parent once by its current status, including accepted requests without attempts. `attempts.total` counts every joined upstream attempt for those parents, so retries can make it larger than `requests.total`. `attempts.pending` is separate. For each of the four existing Token columns, `known_total` sums only stored integer values; `unknown_attempts` counts **terminal** attempts whose column is NULL. A pending attempt does not become a terminal unknown. A known zero remains distinguishable from missing data; a known sum with any unknown attempts is incomplete and must never be labeled a complete total. These are upstream-attempt observations, not unique-request consumption, employee charges, provider invoices, quota, or hard usage limits.

The projection exposes no request/attempt ID, Key plaintext or digest, provider, upstream account, price, cost, currency, balance, bill, policy, prompt, response, or error text. Success and failure responses use `Cache-Control: no-store` and fixed sanitized errors.

## One-snapshot read and failure boundary

A single bounded, read-only SQLite transaction first confirms `access_keys.id` **and** `access_keys.employee_id` match the path selector and verified session, excluding any non-issued self-Key slot. In that same transaction, both aggregate SELECTs constrain the parent ledger simultaneously by `r.employee_id=?` and `r.key_id=?`, plus the frozen window. There is no ownership check on one connection followed by aggregation on another. The transaction has an at-most-five-second request deadline; SQL aggregation and response size are fixed rather than proportional to individual rows. No success header or partial result is written before both aggregates, validation, and transaction commit complete.

Missing/corrupt relevant schema, invalid numeric/status data, SQL integer overflow, query/scan/read/commit fault, or cancellation returns fixed `503 storage_unavailable` with no partial summary. Missing/foreign Key remains `404 not_found`. The transaction gives one snapshot; it does not promise subsequent reads see the same rows. No DDL, ledger write, Key mutation, or upstream/external-service call is introduced.

## Browser, retention, and release boundary

The `/self/` Key inventory offers an explicit “查看已知 Token” action for the selected Key only; loading the list never fans out into per-Key summary requests. The UI labels known Token as upstream-attempt observations, shows all four known/unknown categories and pending attempts, and never calls them complete usage, billable totals, or compliance evidence. It continues to hide Key policy. The selected summary remains only in component memory and is cleared on Key switch, login, logout, session/account change, unmount, or failed fetch; a late response cannot restore stale data. Desktop and 390 px rendering must not persist identities, Token values, or session material in localStorage, sessionStorage, URL, or a service-worker cache.

The source data is existing `access_keys`, `accounting_requests`, and `accounting_attempts`; no new stored personal data or retention timer is added. Existing ledger/WAL, backups, and restored snapshots retain their base behavior; hiding this projection is not forensic erasure. Operators must settle notice, role access, backup/restore, and retention before production enablement. GOV-02 remains open; otherwise leave self-service off and use administrator-only usage management.
