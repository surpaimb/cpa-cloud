# ID-05 employee self-service Key inventory contract

Status: independently specified development-preview increment, default off. This extends the [self-service foundation](employee-self-service-foundation-contract.md) and [password change](employee-self-password-change-contract.md), but does not complete GOV-02 or authorize production use.

## Scope, provenance, and roles

An existing, active, admin-enrolled employee with a valid independent self session may read minimal metadata for **their own existing** API Keys in `/self/`. The server obtains the employee ID only from the verified session; the request has no employee ID or Key ID parameter. Admin sessions, employee model API Keys, and another employee's self session cannot substitute. The existing `--employee-self-service-enabled` flag gates the API and page; when false, `/self/` and `/self/api/v1/keys` remain 404. Admin Key creation, list, policy, revocation, and model authorization semantics are unchanged. This increment adds no DDL, admin setting, new third-party dependency, real-provider call, self Key creation, plaintext redisplay, rotation, revocation, usage/billing, membership, payment, registration, email, SSO, or recovery.

The implementation and tests are newly authored from this contract and existing CPA Cloud specifications, not copied or ported from archived CPA, CLIProxyAPI, Sub2API, or nearby reference repositories. Public behavior references: [Go net/http](https://pkg.go.dev/net/http), [Go database/sql](https://pkg.go.dev/database/sql), [SQLite SELECT](https://www.sqlite.org/lang_select.html), [SQLite isolation](https://www.sqlite.org/isolation.html), and [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339). The existing Go, SQLite driver, React, and test dependencies retain their recorded third-party licenses; no dependency license is transferred to this source.

## GET /self/api/v1/keys

The endpoint is a read-only `GET` behind the existing `requireSelf` boundary: optional Origin, if present, must match; current session digest, absolute expiry, and current employee active state are checked before query. It does not accept a request body or an employee selector. Query parameters are only `limit` and `cursor`, each at most once; unknown/duplicate parameters and malformed values return sanitized `400 invalid_request`. Absent `limit` means 20; explicit limit is ASCII decimal `1`–`50` without sign, whitespace, or leading zero. Absent cursor means the first page; an explicit empty cursor is invalid. The cursor is an opaque versioned base64url encoding of the last emitted Key ID, at most 180 characters, canonically encoded, and decoded to a bounded valid Key identifier. It is a position, not an authorization token. Query authorization always includes the session employee ID, even for attacker-supplied cursors.

The successful `200` response is exactly `{ "items": [...], "next_cursor": string|null }`. Each item is exactly `{ "id", "name", "created_at", "expires_at", "revoked_at", "status" }`; nullable expiry/revocation times are JSON null. Times are valid RFC3339 timestamps normalized to UTC. `status` is `revoked` when `revoked_at` is non-null, otherwise `expired` when `expires_at` is at or before the server's evaluation time, otherwise `active`. Revocation wins over expiry. The status is descriptive, not a new authorization decision. No response includes Key plaintext, selector, digest, operation ID/fingerprint, policy/source restrictions, employee note, upstream, billing, usage, or any other field. No Key plaintext can be recovered from storage or shown again, including old Keys. `Cache-Control: no-store` applies on success and failure.

Pages use `WHERE employee_id = <verified session employee> AND id > <cursor ID>` with binary ascending Key ID order and a maximum of 51 rows per query to detect a following page. This order is stable for existing IDs. A page is read in one SQLite SELECT statement; separate pages are **not** a snapshot. A concurrent insertion with an ID greater than the cursor may appear on a later page, while one with a smaller ID may not. Revocation or expiry between pages may change a later page's status. Clients can restart from page one for a fresh view. No total count or cross-employee existence hint is returned.

Before writing any success header or item, the handler reads, scans, validates, and closes the entire bounded result. Missing/corrupt schema, wrong field type, invalid ID/name/time, query/scan/iteration/close failure, or request cancellation fails closed with a fixed `503 storage_unavailable` response and no partial items or secrets. Auth failures remain `401 authentication_required`; disabled/expired/logged-out/restarted invalid sessions do not reach the inventory query. The browser shows a fresh error and does not retain a stale inventory on failed reads or after account/session changes.

## Browser and data boundary

The existing `/self/` page shows only the employee's own profile and a compact read-only Key inventory with status and timestamps. It supports an explicit “load more” action and renders at desktop and 390 px without exposing hidden policy or credentials. It does not store session, cursor, or Key metadata in localStorage, sessionStorage, IndexedDB, URL, or service-worker cache. No Key action control is offered. The admin page must no longer claim that all Key data is admin-only; it should accurately describe this metadata-only exception.

The data inventory is existing `access_keys.id`, `name`, `created_at`, `expires_at`, and `revoked_at`; computed status is transient. There is no new persisted personal data or retention timer. Existing Key rows, SQLite WAL pages, backups, and any restored snapshot follow the base Key/backup retention behavior; this feature does not delete them or claim forensic erasure. Access expands only to the Key owner with active self credentials; administrators retain their existing access. Operators must settle notice, role access, backup/restore treatment, and retention before production enablement. GOV-02 remains open. If those obligations cannot be established, leave self-service off and use the existing admin-only Key management flow.
