# ID-05 employee self Token summary contract

Status: independently specified development-preview increment, default off. This extends the [self-service foundation](employee-self-service-foundation-contract.md), [password change](employee-self-password-change-contract.md), [Key inventory](employee-self-key-inventory-contract.md), and [request activity](employee-self-request-history-contract.md). It does not settle GOV-02 or authorize production use.

## Scope, source, and access

An existing, active, admin-enrolled employee with a valid independent self session may read a minimal Token summary for **their own** accepted model requests. The verified session supplies the only employee ID; no request parameter can select an employee, Key, provider, account, model, status, or currency. Admin sessions, employee model API Keys, anonymous callers, and another employee's self session cannot substitute. The existing `--employee-self-service-enabled` flag gates the page and endpoint and remains false by default. This increment adds no DDL, configuration, ledger write, Key mutation, membership, payment, provider call, package, or deployment. The administrator usage API retains its existing semantics and authorization.

The implementation and tests are newly authored from this contract and existing CPA Cloud specifications, not copied or ported from archived CPA, CLIProxyAPI, Sub2API, or adjacent reference repositories. Public behavior references: [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339), [Go net/http](https://pkg.go.dev/net/http), [Go database/sql transactions](https://pkg.go.dev/database/sql#DB.BeginTx), [SQLite read transactions](https://www.sqlite.org/lang_transaction.html), and [SQLite integer `sum()` overflow](https://www.sqlite.org/lang_aggfunc.html). Existing Go, SQLite driver, React, and test dependencies retain their recorded third-party licenses; no new dependency or SDK is introduced.

## GET /self/api/v1/usage/summary

This read-only `GET` uses the existing `requireSelf` boundary: optional Origin must match when present, and live self session digest, absolute expiry, and current active employee status are checked before a ledger read. It accepts no body, including unknown-length HTTP/2 bodies. Its only query keys are `from` and `to`, each at most once and required together. Unknown, duplicate, empty, malformed, fractional, or oversized parameters return fixed `400 invalid_request` without data. Explicit bounds are whole-second RFC3339 with a zone, normalized to UTC, and define `[from,to)` with `from < to` and duration at most 31 days. With neither bound, the server freezes a recent 24-hour window ending at the next UTC second, matching the request-activity default. There is no cursor, continuation, or client-supplied identity.

The successful `200` response has exactly this shape, with all counts and sums canonical nonnegative decimal strings:

```json
{"from":"2026-09-30T00:00:00Z","to":"2026-10-01T00:00:00Z","requests":{"total":"2","pending":"0","succeeded":"1","failed":"1","cancelled":"0","interrupted":"0"},"attempts":{"total":"3","pending":"0","input_tokens":{"known_total":"15","unknown_attempts":"1"},"output_tokens":{"known_total":"2","unknown_attempts":"1"},"cache_read_tokens":{"known_total":"0","unknown_attempts":"2"},"cache_write_tokens":{"known_total":"0","unknown_attempts":"2"}}}
```

The window filters **parent** `accounting_requests.started_at` by actual UTC nanosecond order, using the existing normalized nine-digit SQL time key rather than lexicographically comparing variable-width RFC3339Nano text. `requests` counts each matching parent once by its current status, including accepted requests with zero attempts. `attempts.total` counts every joined upstream attempt for those parents; retries can make it larger than `requests.total`. `attempts.pending` is separate. For each of the four Token columns in existing `accounting_attempts`, `known_total` sums only stored integer values and `unknown_attempts` counts **terminal** attempts whose column is NULL. Pending attempts have no Token values and do not count as terminal unknown. A known zero is distinguishable from missing data; a known sum with any unknown attempts is incomplete and must never be labeled a complete total. This is upstream-attempt accounting, not unique-request consumption, employee charges, a provider invoice, quota, or a hard usage limit.

The endpoint exposes no request/attempt ID, Key plaintext, provider, upstream account, price, cost, currency, balance, bill, prompt, response, error text, or arbitrary SQL row. Responses, including errors, use `Cache-Control: no-store`. The browser uses the fixed labels “已知 Token（上游尝试）” and “未知尝试”, shows the four categories and pending attempts, and does not call these totals complete, billable, or compliant.

## Snapshot, failure, and persistence boundary

Both aggregate reads execute in one bounded (at most five-second) read-only SQLite transaction. The service validates count types and nonnegative relationships before writing a response. It uses integer `sum()`, not floating-point `total()`: SQL integer overflow, wrong numeric type, malformed relevant schema, missing table, query/scan/commit error, or cancellation is a fixed `503 storage_unavailable` with no partial response. The result is one transaction snapshot, not a promise that a later read sees the same state. Writes committing during a read may appear only in a later request. The service does not create, modify, or delete accounting facts.

The browser keeps summary only in component memory. It clears it on login, logout, account/session change, unmount, and a failed fetch; late responses cannot restore stale data. It renders at desktop and 390 px without putting identity, Token sums, or session material in localStorage, sessionStorage, URL, or a service-worker cache. The existing request-history and Key sections keep their independent read/failure behavior.

The source data is existing `accounting_requests` and `accounting_attempts` rows. This feature adds no stored personal data or retention timer. Existing ledger rows, SQLite WAL pages, backups, and restored snapshots follow their base retention behavior; hiding the summary is not forensic erasure. Operators must settle employee notice, role access, backup/restore, and retention before production enablement. GOV-02 remains open; otherwise leave self-service off and use administrator-only usage management.
